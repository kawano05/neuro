# 研究内容と評価設計メモ

## 研究テーマ

ニューロノードを用いたiPad向け支援アプリの研究開発と実用化検討。

## 研究目的

ニューロノードおよびiPadのSwitch Controlで操作しやすい支援アプリを、Webアプリとして先行開発し、CapacitorでiOSアプリ化する。Web版とiOS版、または参照構成と最適化構成を比較し、重度運動障害や発話困難のある利用者にとって操作負担の少ないUI/UX要件を明らかにする。

2026-08-20から、利用者向けリズムL1/L2は `slot-v1` の視覚運動タイミング・
逐次停止課題へ置換した。主要仮説（`fishing` の平均反応時間）は変更せず、
スロットは副次評価とする。固定仕様は `docs/slot-game-replacement-plan.md` を参照する。

## 関連研究・事例から見た評価軸

### 1. スイッチ走査研究

単一スイッチ走査では、単に「正解したか」だけではなく、時間、入力回数、エラーの種類を分けて記録する必要がある。

- タスク完了時間
- スイッチ入力回数
- 入力間隔
- 誤選択率
- タイミングエラー
  - 見逃し: 目標項目がハイライトされたのに押せなかった
  - 早押し: 目標より前に押した
  - 遅押し: 目標を過ぎてから押した
- スキャン間隔
- エラー修正や戻り操作の回数

参考:
- Koester and Simpson, Scanning Wizard: https://pmc.ncbi.nlm.nih.gov/articles/PMC5967995/
- Bhattacharya et al., User errors on scanning keyboards: https://www.sciencedirect.com/science/article/abs/pii/S0953543808000246

### 2. AAC・VOCA研究

AACインターフェースの評価では、速度と正確性に加え、ユーザビリティや主観的負担も評価される。

- 情報伝達速度
- エラー率
- スイッチ入力数
- 1語または1メッセージあたりの入力数
- 主観的負担
- ユーザビリティ
- 会話や意思表示が成立したか

参考:
- Shea et al., Evaluation of an AAC Interface: https://journals.sagepub.com/doi/10.1177/15553434221078215

### 3. 重度・重複障害児向けワンタップ教材

教育実践系の研究では、操作性能だけでなく、児童生徒が自分で選択・決定できたか、興味関心を示したか、課題設定を変えられるかが重要になる。

- 正誤判定
- 選択肢数
- 課題達成
- 興味・関心
- 自己選択・自己決定の変化
- 支援者による観察記録

参考:
- 北村・菊池, ワンタップ教材アプリ「どーれかな？」: https://cir.nii.ac.jp/crid/1050001339172174336

|---|---|---|---|---|

## 計画書から見た独自要素

仙台高専の学習支援ソフトとの差別化は、教材数そのものよりも、以下を研究対象に含める点に置く。

- Web先行開発からCapacitorによるiOSネイティブ化までを一連の研究手順として扱う
- Web版/iOS版、参照構成/最適化構成の比較条件を明示して評価する
- 病院・施設の共有iPadを想定し、Guided Accessによる単一アプリ運用を検証する
- App Store公開候補版として、ローカル動作、公開素材、運用説明まで確認する
- 支援者の観察メモを評価データに組み込み、現場運用上の課題を抽出する

Webアプリには、この独自性を可視化するために「実用化研究」画面を追加する。ここで研究条件プロファイル、公開候補チェック、現場運用メモを管理し、効果測定の条件や観察メモへ反映できるようにする。

## 実験タスク案

1. スイッチ教材を5回入力する
2. マッチング問題を1問正解する
3. VOCAで「痛いです」を選択する
4. 文字学習を1問正解する
5. `slot-l1` で1本のリールを8回止める
6. `slot-l2` で3本を左から右へ4ラウンド止める
7. ポイントスキャンで目標位置を選択する
8. UFOキャッチャーでX/Y走査を止め、目標中心との距離を測る
9. さかなつりで変動する待機時間後の本アタリに反応し、偽アタリを見送る

各タスクをWeb版とiOS版、または参照構成と最適化構成で実施し、同じ評価項目で比較する。

## iOS Switch Control対応を見据えた操作訓練

iOSのSwitch Controlでは、項目を順にハイライトして選択する項目スキャンに加えて、画面上の一点を十字カーソルで指定するポイントスキャン系の操作がある。さらに、選択後のアクションとしてタップ、ドラッグ、スクロールなどを使う場面がある。

本研究のWeb版では、iOS実機検証の前段階として以下の操作訓練を実装する。

- 項目スキャン訓練: ボタンやカテゴリを順に選ぶ
- ポイントスキャン訓練: 縦横カーソルを止めて目標位置を指定する
- タップ訓練: 指定された位置を選択する
- ドラッグ訓練: 開始点から目標点へ移動する操作を段階的に行う

Web版ではSwitch Controlそのものを完全再現するのではなく、操作過程を模擬し、完了時間、入力回数、成功率、ズレ距離、誤選択、介助回数を記録する。iOS版では実際のSwitch Controlを用いて同じタスクを行い、Web版の模擬評価と実機評価を比較する。

## 事前固定プロトコル（データを取る前に決めておくこと）

**この節は、最初の1件を測る前に確定させる。** 確定した日付を各項目に書き、
以後は変更しない。変更する場合は、それまでのデータと分けて扱う。

理由: 主要評価項目や除外基準をデータを見てから決めると、たまたま差の出た
指標を選べてしまう。少人数研究では指標が1つ増えるだけで「何かが有意に見える」
確率が跳ね上がるので、事前に1本へ絞っておくことが、結論を主張できる条件になる。

> **確定状況**: 以下は既定案。`主要仮説`と`主要評価項目`は研究者の署名が要る
> （指導教員の確認を経て、この行を「確定 YYYY-MM-DD」に置き換える）。
> それ以外の項目（条件順・除外基準・解析単位）は、この案のまま運用してよい。

### 1. 主要仮説（1つだけ）

> 最適化構成は参照構成に比べ、**単純反応課題（fishing）の平均反応時間**を
> 参加者内で短縮する。

**なぜこれを主要に置くか（採否の判断材料）**

- **参加者が脱落しにくい。** fishing は聴覚だけで成立する。slotとcraneは
  `visualRequired` で、視覚注視の難しい参加者は `hideVisualTasks` により
  そもそも実施できない——主要評価項目に置くと、参加者ごとに主要項目が
  無い／有るがまだらになる。
- **指標が1つの数字に落ちる。** 反応時間は ms 単位の連続量で、参加者内の
  前後比較にそのまま使える。走査選択の成否は試行数が少なく、比率の
  参加者内比較は少数例で不安定になる。
- **測定の前提が最も軽い。** slot-l2は「目標を見て3本を順に止める」規則と
  持続的な画面注視を要求するが、単純反応は「音が鳴ったら押す」だけである。
  このためslot-v1への置換後も、主要仮説はfishingのまま維持する。

**副次評価項目**（主要の裏づけとして見るが、これ単独では結論にしない）

1. fishing の反応時間の**ばらつき**（SD）
2. slot-v1 の絶対ずれ中央値・符号付き平均ずれ（実施できた参加者のみ）
3. slot-l2 の1本目／2本目／3本目別絶対ずれ、timeout、余分な入力、完遂時間
4. crane の目標中心からの距離、X/Y 位相所要時間（実施できた参加者のみ）
5. gonogo の commissionRate
6. 主観評価（負担感・操作しやすさ・集中/関心）と支援者の介助回数

副次項目に有意差が出ても、主要仮説の結論は変えない。副次は「主要の差が
どこから来たか」を説明するために見る。

### 2. 解析単位

**参加者 × 条件を1つの観測**とする。試行を1観測として数えない。

これは少人数研究でいちばん壊れやすいところ。1人が60試行やれば n=60 に
見えるが、同じ人の試行どうしは独立ではないので、それで検定すると
p 値がいくらでも小さくなる。参加者ごとにまず1つの要約値（例: その条件での
反応時間の中央値）を作り、その要約値どうしを比べる。

n はあくまで**参加者の人数**。

### 3. 条件順（カウンターバランス）

参加者内クロスオーバー。参加者を組み入れ順に交互へ割り付ける。

| 参加者 | 1日目 | 2日目 |
|---|---|---|
| 奇数番目 | 参照構成 | 最適化構成 |
| 偶数番目 | 最適化構成 | 参照構成 |

- 同日に両条件を詰め込まない（疲労が後の条件へ乗る）。
- 同一参加者の2日は**同じ時間帯**に置く（覚醒水準の日内変動を条件と
  交絡させない）。
- 課題の実施順は全参加者で固定する: **fishing → gonogo → slot-l1 → slot-l2 → crane**。
  順序を参加者ごとに変えると、少人数では順序効果と条件効果が分離できない。
  slot-l1を先に置き、1入力1停止が成立してからslot-l2へ進む。この順序は
  データ収集開始前に指導教員確認で確定し、変更後のデータとは分ける。

### 4. 除外基準（測る前に決める）

**回（セッション）単位で外すもの**——いずれもアプリが記録している値で機械的に判定できる。

| 条件 | 判定に使う列 | 理由 |
|---|---|---|
| 中断した回 | `aborted = true` | 試行数が計画と違うので比率の意味が変わる |
| れんしゅうの回 | `difficultyMode ≠ measure` | パラメータが参加者ごとに違う |
| slot-v1固定条件でない回 | `protocolVersion ≠ slot-v1` または `seed ≠ slot-measure-01` | 新旧パラダイムや測定条件を混ぜない |
| 旧SMSで画面から拍の手がかりを出した回 | `visualGuidance = true` | 聴覚同期を測った回ではない。slot-v1には適用しない |
| 通過音を鳴らした回（crane） | `audioGuidance = true` | 画面を見ずに解けるので視覚課題の成績ではない |
| 成立確認を通していない回 | `measurementReadiness = overridden` | 成績の低さの原因を分けられない |
| 端末が違う回 | `deviceViewportWidth` ほか | 刺激の実寸・視距離・音の出方が変わる |

**試行単位で外すもの**

- `excluded = true`（立ち上がりの拍。キャリブレーションでは先頭4拍）
- `judgment = falseStart`（合図前の入力。反応時間が定義できない）

**参加者単位で外すもの**

- 両条件のうち一方でも、除外後に有効な回が **1回も残らなかった**参加者
- 途中で研究参加を取り下げた参加者

除外後に残った件数は、条件ごと・参加者ごとに必ず報告する（何を落としたかを
書かない除外は、結果の選び取りと区別がつかない）。

### 5. 統計処理

参加者数は数名を想定する。この規模では群としての有意差検定は成立しない
——**症例集積として、参加者ごとの変化を1人ずつ示す**。

- 主要な提示は、参加者ごとの2条件の値を並べた図と表（個人の線をつないだ図）。
- 「変化した」と言う基準も事前に決める: その参加者の**参照構成での回内SD の
  2倍**を超える差を、測定誤差を超えた変化とみなす。日ごとの調子の差を
  変化と呼ばないための線。
- 群平均と検定を出す場合は副次的な位置づけとし、n と検定手法を明記する。
- 欠測は補完しない。欠測のまま「その参加者のその条件は無し」と示す。

### 6. 成立確認（測定に入る前の前提）

現行 `src/lib/readinessCheck.js` は、gonogo、fishing、旧SMSの3条件を参照する。
slot-v1への置換によって新規利用者は利用者ホームから旧SMSを実施できないため、
第3条件をslotへ置換する閾値は**未確定**である。データを見てから閾値を作らず、
予備試験と指導教員確認で別途固定する。

| 現在実装済みの確認 | 根拠にする課題 | 通る条件 |
|---|---|---|
| 高い音と低い音を聞き分けられる | gonogo | Goで押す割合とNo-Goで押す割合の差が0.3以上 |
| 合図に対して意図して押せる | fishing | 平均反応時間が120〜1500ms |
| 旧・規則を続けられる | 旧sms | ずれSDが一様分布SDの0.6倍以下 |

slot用の成立条件が確定するまでは、測定を強行した回を
`measurementReadiness = overridden` として記録し、主解析から外す。候補として
slot-l1完遂、timeoutなし、余分な入力上限、絶対ずれの分布を検討できるが、
本書では閾値を確定済みと扱わない。

### 7. アプリ側で固定されていること

事前固定を人の運用に頼らず、アプリが構造的に守っている部分。
- slotのそくてい回は `slot-v1`、cycle 3200ms、許容幅±220ms、
  L1 8round、L2 4round、4周期timeout、seed `slot-measure-01` を固定する。

- そくていの回は `MEASUREMENT_PROTOCOL`（`src/lib/difficultyMode.js`）で
  パラメータが固定され、支援者は変更できない（操作子は無効化され、理由が
  画面に出る）。
- キャリブレーションは支援者の難易度設定を一切受け付けない
  （`PROTOCOL_LOCKED_GAME_IDS`）。
- 測定条件は禁止せずに記録する。条件は `session.config` → `state.js` の
  sanitize → CSV の3経路すべてを通る。

**まだ人の運用に頼っている部分**（アプリが強制していないので、手順書で担保する）

- 条件順のカウンターバランス
- 課題の実施順
- 同一時間帯での実施
- 端末を参加者内で変えないこと

## 分析方針

主な比較指標は以下とする。

- タスク完了時間が短くなるか
- 入力回数が減るか
- slot-v1 の絶対ずれ中央値と符号付き平均ずれが小さくなるか
- slot-l2でリール順に精度低下、timeout、余分な入力、完遂時間の増加があるか
- 誤選択率が下がるか
- タイミングエラーが減るか
- 支援者の介助回数が減るか
- 主観的負担が下がるか
- 操作しやすさ、集中・関心が上がるか
- crane の目標距離とX/Y位相時間が短縮するか
- fishing の平均反応時間とばらつきが小さくなるか
- fishing のフライング率・偽アタリへのcommission率が下がるか

少人数研究になる可能性が高いため、平均値だけでなく、参加者ごとの変化を重視する。特に、重度運動障害のある利用者では個人差が大きいため、Web版とiOS版の比較、または同一利用者内での前後比較を中心に扱う。

crane はiOS Switch Controlのポイントスキャン、slot-l2は1入力1停止を順に
完遂する操作と構造的に近い。一方で両者は視覚注視を要するため、利用者の
残存機能に応じて `hideVisualTasks` で除外する。fishingとgonogoは聴覚中心で
実施でき、旧rhythmデータはslot-v1と分けて履歴解析する。
