## 通底している設計判断

### 1. 測定を変える設定は「禁止せず、記録する」

支援者が触れる設定のうち、**測っているものを変えてしまう**ものは条件として
毎回記録し、CSVの**末尾**に列として出す（既存の列位置は動かさない）。

| 条件 | 既定 | ONで何が変わるか |
|---|---|---|
| `visualGuidance` | OFF | 円が拍を予告し、押した後にずれが出る → 聴覚だけへの同期でなくなる |
| `craneAudioGuidance` | OFF | 目標の座標が音になる → 画面を見ずに解ける |
| `difficultyMode` | practice | そくていでは全パラメータが protocol 固定 |
| `textMode` | kana | 手順の説明が読めるかは成績に効きうる |
| `device`（viewport/dpr） | 記録のみ | iPad とスマホで視距離・刺激の実寸・音の出方が変わる |
| `measurementReadiness` | n/a | 成立確認を通さずに測った回は、成績の低さの原因を分けられない |

**記録は3経路すべてを通さないと意味がない**: `session.config` → `state.js` の
sanitize → CSV。どれか1つ欠けると条件を後から区別できない。これは実際に
2回やらかしている（`visualGuidance` を sanitize から落とした／`device` を
記録したのに CSV に出していなかった）。新しい条件を足すときは3経路を確認する。

`measurementReadiness` を足したときは、sanitize を落とすと落ちるテストを
先に確認してから入れた（`tests/data-integrity.test.mjs` の
「a session keeps its readiness state across a reload」）。

### 2. 条件を増やすだけでは交絡は消えない → 名前つきの束にする

条件が増えるほど層別すべきセルが増え、少ない参加者では空のセルばかりになる。
そこで `difficultyMode`（measure / practice）に畳んだ。**解析ではまず
`difficultyMode == "measure"` の回だけを見ればよい**、が狙い。

そくていの回はむずかしさのつまみが無効化され、走査対象からも外れ、
その理由が画面に出る（効かない操作子を黙って置かない）。

`MEASUREMENT_PROTOCOL` は `content.js` のプリセットと**別に持っている**。
訓練の都合でプリセットを調整しても測定の条件は動かない。

### 3. 「動くが伝わらない」型の欠陥を疑う

このリポジトリで繰り返し出ている欠陥の型:

- 効かない操作子が理由なく置かれている
- `display:` を当てて `hidden` 属性を打ち消す（**今回も再発させた**）
- 記録しているのに書き出していない
- テストが通っているのに何も検査していない
- **表示している文字列を状態として読む**（fishing が
  `statusEl.textContent !== "しずかに まとう"` で分岐していた。表記を
  切り替えた瞬間に成り立たなくなる。キーで持つように直した）

### 4. `t` の影 — 乱数でしか踏まない経路の欠陥

i18n の張り替えで、`t("crane.carrying")` を **`const t = 進捗0..1` の
ブロックの中**で呼んだ。t は数値なので `t is not a function` で rAF が止まり、
アームが景品口の手前で永久に固まる。同じブロックの `if (t >= 1)` は例外すら
出さず、黙って偽になり続けていた。

質が悪いのは**掴めた試行でしか通らない**こと。スモークは掴めるかが乱数なので、
落ちたり落ちなかったりした。「たまに落ちるテスト」を flaky と決めつけると
本物を見逃す——実際、最初は環境要因だと思って2回素通りさせている。

見つけ方は、推測をやめて繰り返し実行し `pageerror` を拾ったこと
（`test-results/probe-crane-stall.mjs`）。16回中3回で再現し、原因が1行で出た。

再発防止として `tests/i18n.test.mjs` に、ctx から `t` を受け取っているファイルの
**その行より後**でローカルに `t` を作っていないかを見る静的検査を入れた
（モジュール直下の `easeInOut(t)` は文言の t が見えないので対象外）。

## 今回直した主なもの（理由つき）

### 測定の妥当性に関わるもの

- **パルス円の「溜め」が拍の予告になっていた。** 設計書が「拍に同期して動く
  視覚を増やさないこと自体が要件」と書きながら、同じ設計書が予告の曲線を
  規定していた。`visualGuidance` に紐づけて解決（着地と沈みは拍が起きたことを
  伝えるだけなので常に出す。溜めだけが予告になる）。
- **crane の `maybePassTone` が目標座標を聴覚キューへ翻訳していた。** 画面を
  見ずに解けるので `visualRequired` の前提が崩れる。条件化（既定OFF）。
- **音が鳴らない状態でセッションを開いていた。** AudioContext が無い場合に
  加えて、**あるのに鳴らない**場合（iOS の suspended / interrupted）も止める。
  さかなつりは実測で「刺激を一度も出していない回のデータ」を2件記録していた。
- **オフセット分布が課題・テンポ・参加者を1つの山に混ぜていた。** 課題×テンポ×
  参加者で図を分けた。
- `prefers-reduced-motion` が rAF のパルスに効いていなかった。

### 走査・レイアウト

- **走査の現在位置がドックの裏に隠れていた**（スマホでタイルまるごと182px）。
  `scroll-margin` ＋ページ走査（3項目＋「つぎのページ」、循環）。
- 横向きでモバイル用の圧縮が丸ごと効いていなかった（`max-width:820px` に
  紐づいていて 844px 幅の横向きが条件に入らない）。高さ基準のルールを追加。
- 効果測定タブの横スクロール、44px 未満のタップ標的、文字入力中のドック退避。

### 難易度

旧値は段になっていなかった。**L1→L2 で入力密度が5.6倍**に跳び、gonogo は L2 より
運動負荷が低かった（0.52倍）。L1 は10回押すのに68秒。

テンポを50に揃えて、段のあいだで変わるのを**課題の構造だけ**にした。

| 課題 | 1回の長さ | 押す回数 | 入力密度 | 上がる軸 |
|---|---|---|---|---|
| リズム れんしゅう | 34秒 | 8 | 0.24回/秒 | — |
| たかいおとだけ | 28秒 | 12 | 0.43回/秒 | 認知 |
| リズム つづけて | 24秒 | 16 | 0.67回/秒 | 運動 |

軸が1本でないのは意図（押さない試行がある課題の運動負荷が低いのは当然で、
2軸を同時に上げないための設計でもある）。

#### A の残り: 署名が要る2項目

主要仮説の既定案は「最適化構成は参照構成に比べ、fishing の平均反応時間を
参加者内で短縮する」。fishing を主要に置いたのは、聴覚だけで成立して参加者が
脱落しにくく、指標が ms の連続量1つに落ちるから（crane は `visualRequired` で
実施できない参加者が出る）。採否の判断材料は research-summary に書いた。
条件順・除外基準・解析単位は案のまま運用してよい。

#### B の判断（cued → continuous）

`test-results/probe-calibration-mode.mjs` で推定量の性質を比べた。モデルによる
検討で実測ではないが、比べているのは推定量の偏りと分散なので判断材料になる。

- **cued の危険は見えない偏り。** 試行ごとにカウントインでリセットするので
  位相修正の連鎖が切れ、予測押しと反応押しが同じ分布に混ざる。反応押しが
  20%混じると +20ms、30%で +46ms、50%で +146ms ずれる。10試行では二峰性を
  検定できないので**データを見ても気づけない**。しかもこの値は
  `baselineOffsetMs` として全セッションの判定窓中心に効く。
- **continuous の代償は見えるばらつき。** 位相修正過程の自己相関ぶん、
  理想条件でも分散が大きい（sd 16.7ms → 28.1ms）。ただし拍数で減らせる。
- **偏りは検出も補正もできず、分散は増やせば減る。** だから continuous。

ついでに1回が 93.6秒 → 33.6秒に短くなり、有効試行は 10 → 20 に増えた
（bpm50 / countIn4 / targetBeats24 / 先頭4拍を除外）。

判定窓は continuous の制限を受ける側になった（bpm50 で W=540）。

### 実際に遊んでみて出た指摘（2026-08-17 追記）

開発サーバーで通しで遊んでもらった結果、2件の指摘が出て、そこから3つ直した。

#### 1. リズム練習の指示が課題と食い違っていた

画面に出ていたのは `おとに あわせて おそう`——これは毎拍押す rhythm-l2 の
文言で、L1 の課題（低音2回のあと**高音のときだけ**押す）とは別のことを
言っている。レディ画面では3行で正しく説明しているのに、**始まった瞬間その
情報が消える**。gonogo は最初から `たかい おとの ときだけ おそう` と出して
いたので、L1 だけが抜けていた。

さらに悪いことに、パルス円は低音でも高音でも同じ動きなので、画面から
押しどころを読む手がかりがひとつも無い。

直し: `stage.rhythm-l1` を「低い音のあと、高い音で押そう」に。**規則の説明で
あって拍の予告ではない**（いつ来るかは書いていない）ので、手がかりの設定に
関わらず常に出してよい。測定しているもの（聴覚キューへの同期）は変わらない。

進捗表示も `のこり 8` → `のこり 8かい` に。L1 は1回押すまでに4.2秒かかるので、
単位が無いと秒数と取り違えて「進んでいない」と見える。

#### 2. 設定が1ページに多すぎた → タブに分けた

（最初は折りたたみで対応したが、「開いてから探す」が残るので面を分けた）

実測 **2438px = 3.4画面ぶん**、9グループ・18操作子。ふだん触る設定
（走査・音・見え方・出すあそび）が、めったに触らない測定用のつまみに
埋もれていた。

直し: 4つのタブに分けた。**配分の基準は「1面が1画面に収まること」**——
タブに分けても面が長ければ、結局スクロールで探すことになる。

| タブ | 中身 | iPad実測 |
|---|---|---|
| そうさ | 走査（スイッチで選ぶ）・出す遊び | 0.47画面 |
| 見え方・音 | 音と言葉・見え方 | 0.70画面 |
| むずかしさ | リズム・UFOキャッチャーの難易度 | 0.96画面 |
| そくてい | 測定開始・研究者向け・この回の使い方・成立確認 | 0.56画面 |

**iPad では4面すべてスクロール不要**（元は1ページ 2438px＝3.4画面）。
スマホでは面によってスクロールが残るが、探す範囲は1/4になっている。

見えていない面の操作子は走査の輪から自動的に外れる——scan.js は
`rect.width > 0` で絞るので、hidden の中の `[data-scan]` は対象外になる。

**面をまたいで伝えるものがある。** むずかしさのつまみが固定される理由
（measureModeNotice）は、切り替えが「そくてい」タブにあっても**つまみと
同じ面**に置く。効かない操作子を見ているのはその面なので、理由がそこに
無いと支援者は別の面を探しにいく。加えて、いま測定の回であることは
「そくてい」タブ自体に印を出す（別の面を見ていても分かるように）。

### 支援者編集ロックを廃止した（2026-08-17）

何を守っていたか: 設定画面の操作子は走査対象（実測16個）で、支援者が設定を
開いているあいだも走査は動き続ける。そこで利用者がスイッチを押すと、
ハイライト中の項目が切り替わる。それを防ぐため既定で全操作子を disabled に
していた。

**やめた理由**:

1. 利用者は自力で支援者の世界へ入れない（`#homeSupporterMenu` は走査対象外の
   タップ専用）。入口が閉じているので、中で守る必要が薄い。
2. **iOS の Switch Control にはポイントスキャン**（画面上の任意の座標を指す
   操作）がある。アプリ側の `[data-scan]` の輪は、その世界では到達範囲の
   境界になっていない——解除ボタン自体も押せてしまう。守りとして成立して
   いない仕組みを、支援者の毎回の一手間と引き換えに置いていた。

代わりに残っているもの: 支援者の世界への入口がタップ専用であること、
破壊的な操作（訓練記録の消去・候補値の保存）が走査対象外であること。
**「無効化されているが輪には居る」ではなく「輪に入っていない」で守る。**

消したもの: `#supporterEditToggle` / `#supporterLockNotice` /
`data-supporter-edit` / `applySupporterEditState` / `SUPPORTER_EDIT_VIEWS` /
`SUPPORTER_UNLOCK_VIEWS` と、対応する CSS・スモーク検査。

#### 3. 支援者の画面の表記が2種類混ざっていた

実測: 設定は10見出し中7つ＋項目名4件、評価ログは4見出し中3つが分かち書きの

### 利用者向けの表記を「総ルビ」に畳んだ（2026-08-17）

漢字モードとかなモードを別々に持つのをやめ、**ルビ付き漢字1つ**にした。

**なぜ**: 漢字は語の境界を作るので読める人には漢字が速い。読めない人には
かなが要る。以前はどちらかを支援者が当てにいく必要があり、外すと読めない
画面になっていた。総ルビなら同じ画面で両方が成り立つ（特別支援教育の教材で
標準的な作り）。表記は測定条件なので、条件が1つ減る利点もある。

**作り**: 記法は `漢字[よみ]`。1つの記法から画面用（`<ruby>`）と読み上げ用
（プレーン文）の両方を作る——2つを別々に持つと片方だけ直して食い違う。

- `t()` … プレーン文。textContent・読み上げ・aria-label・announce 用
- `tHtml()` … ルビを展開した HTML。画面へ出す用

`t()` をプレーン側にしたのは、取り違えたときの壊れ方が穏やかだから。逆に
すると textContent の場所で `<ruby>` が生で画面に出る。

形態素解析器は使っていない（オフライン動作が要件で辞書を積みたくない。
「音」が おと か おん かは結局人が確かめる）。対象は100文字列・異なり漢字82字
なので手で書いた。

**踏んだ欠陥**: 最初のルビ正規表現が貪欲で、`色[いろ]と音[おと]` の2つ目が
`と音` を本文にした——ふりがな「おと」が助詞「と」の上にまたがって乗る。
本文は `[` の直前の**漢字の連なりだけ**に限定した。画面を見て気づいた欠陥で、
辞書もレンダラも「動いて」はいた。

**largeText との相性**（実測して直したもの）: `.tile-description` は
`clamp(0.95rem, …)` と rem 基準なのに、`body.large-text` は body に 112% を
当てている。rem は root 基準なので**拡大表示が効かない**。ふりがなは本文比
0.55em だったので実測 8.1px まで落ち、拡大表示にしても 8.1px のままだった。
`rt` に絶対値の下限（11px）を置いた。

> なお「largeText が rem 指定の文字に効かない」こと自体は、ルビとは別の
> 既存の問題として残っている（本文側は今回触っていない）。

行間を広げるのは `:has(ruby)` で**実際にルビが乗っている行だけ**にした。
一律に広げると、ふりがなの無い行まで背が高くなって走査対象がドックの裏へ
押し出される。

CSSは**ファイルの末尾**に置いてある。前方に置くと後段の `line-height` に
上書きされる（実際に上書きされて、説明文のふりがなが見出しと詰まった）。

**`textContent` はふりがなも連結する。** `<ruby>横<rt>よこ</rt></ruby>に…` の
textContent は `横よこに…`。表示文字列を読んで比較しているコードは、総ルビに
した時点で全部ずれる（実際、スモークの crane 状態表示とタイル名の照合が
落ちた）。比較する側は `rt` を落としてから読む——`aria-label` はもともと
プレーン文なので、そちらと突き合わせるのが安全。

**`buildGameCtx()` に `tHtml` を渡し忘れると全ゲームが落ちる。** ゲーム側は
ctx から分割代入するので、渡し忘れると `tHtml(...)` が未定義の呼び出しになり
mount() ごと例外。画面はレディ表示のまま固まって、押しても始まらない
（スモークが4課題×4実寸＝16件で即座に捕まえた）。

### 走査対象がドックに隠れる件を直した（2026-08-17）

**症状**: スマホ縦（390x812）でホームのタイル2枚が入力ドックの裏に隠れ、
走査で選べない項目が輪に残っていた。ルビとは無関係（英語表記でも同じ）。

**なぜ検出できていなかったか**: `scanPaging.js` のページ分割は画面高さ
740px 以下で入る。スモークの実寸は 664px（iPhone 14）と 1194px（iPad）で、
**740〜900 の帯を1つも通っていなかった**。`phone-tall`（390x812）を実寸に
足した——検査は 79 → 98 に増えた。

**直しかた（定数を当て直すのではなく、収まったかで決める）**:

タイルの高さは文言の折り返しで変わる（実測 80〜151px）ので、「この画面高さ
なら入る」を定数で当てるのは原理的に無理がある。しきい値は初回描画の
ちらつきを減らす**先読みの当て**に格下げし、最終判定は描いた結果の実測に
した（`views/home.js` の `listOverflowsDock` → `refitIfOverflowing`）。

1. 分割していなければ分割する
2. 分割してもはみ出すなら、1ページの件数を1つ減らす（下限2件）

実測で分かったのは、**ページ送りタイル自身が 63px はみ出していた**こと。
本体3枚は入るのに送りが入らず、送れないのでページを繰れない状態だった。

**許容幅は 24px**（`SCAN_OVERLAP_TOLERANCE_PX`）。実測した重なりは
2px（スマホ横）／8px（iPad・大きい文字ON）／63px（ページ送り）／
182px（旧実装）で、24px はドック高（100px）の1/4・タイル高の1/3未満。
ここを厳しくしすぎると別の害が出る: 8px で分けていたとき、iPad で大きい文字を
入れた瞬間に**選択肢が5つから3つへ減った**。重なりの実害より、選べる数が
減る害のほうが大きい。走査は `scrollIntoView` するので、この幅なら現在位置は
必ず全体が見える。

> 判定は**フォントが確定してから**行う（`document.fonts.ready`）。差し替え前の
> 値で latch すると、本当は入る画面でも分割されたままになる。

### 「大きい文字」が効いていなかったのを直した（2026-08-17）

`body.large-text { font-size: 112% }` だったが、**rem はルート基準**なので
body を拡大しても rem 指定の文字は 16px のままだった。さらに
`body { font-size: 16px }` と px で固定してあったため、継承で決まる em/％ の
文字も止まっていた。実測: タイルの説明は拡大表示でも 14.7px のまま、そこへ
乗るふりがなは 8.1px だった。

直し: 拡大を**ルート**に当て（`:root:has(body.large-text)`）、`body` を
`font-size: 1rem` にした。実測で root/body 16 → 17.92px、説明文 14.7 →
16.5px と、設定が実際に効くようになった。

ふりがなは `max(0.68em, 0.7rem)` で下限も rem 基準にしてあるので、拡大に
連動して大きくなる（比率だけだと 8px 台まで落ちて読めなかった）。

### ルビと iOS 実機（2026-08-17）

**確かめたこと（Playwright の WebKit）**:

- `<ruby>`/`<rt>` は描画され、ふりがなは18/18すべて本文の**上**に乗る
- `ruby-position: over` が効き、`-webkit-ruby-position` も `before` に解決される
- ふりがなの実寸は iPad 12.0px / スマホ 11.3px（下限が効いている）
- 収まり判定（ページ分割）は WebKit の実寸4つで通っている

**Chromium と WebKit で違ったこと**: ルビの乗る行の高さが
**WebKit のほうが約30%高い**（見出し行 79px vs 61px）。ルビの見た目を
Chromium だけで測ると、iOS では想定より詰まる。`probe-ruby-look.mjs` は
Chromium で書いてあるので、レイアウトの判断に使うときは注意する
（収まりの検証はスモークの WebKit 側が担当している）。

**`:has()` 依存を外した**: `:root:has(body.large-text)` と `:has(ruby)` を
使っていたが、`:has()` は Safari 15.4 より前に無い。外れると
**「大きい文字」が黙って効かなくなる**——効かないことに気づけない設定は、
無いのと同じか、それより悪い（支援者は入れたつもりでいる）。
`html.large-text` / `html.text-ruby` をJSで付ける方式に変えた
（`views/settings.js` の applyClasses）。

**実機が無くても調べられたこと**:

1. **VoiceOver がふりがなを二重に読まないか** → アクセシビリティツリーで確認できた。
   WebKit の ARIA スナップショットで、`aria-hidden="true"` あり／なしを比べた:

   ```
   あり（いまの実装）: button "色と音"  / text: 押 すと 色 と 音 が 変 わるよ
   なし（比較対照）  : button "色と音"  / text: 押 お すと 色 いろ と 音 おと が 変 か わるよ
   ```

   読みは確かにツリーから外れている。`aria-hidden` は**効いているし、外すと
   実際に二重になる**——飾りではなく、載せている理由がある。

2. **iOS の自動文字拡大** → `-webkit-text-size-adjust: 100%` を明示した。
   Safari の既定は `auto` で、レイアウト次第で本文だけ勝手に太る。拡大は
   `html.large-text` で管理しているので、OS側と二重に掛かると支援者が入れた
   倍率と画面が食い違う。

3. **`:has()` 依存** → 外した（上記）。

**まだ実機／シミュレータが要るもの**: VoiceOver が「実際に発声するか」は
ツリーだけでは決まらない（ツリーを読むのは VoiceOver 自身で、ルビの扱いには
版差がある）。ツリーが正しいことは必要条件で、そこは満たしている。

### 実機なしで iOS を動かす — シミュレータのCI（2026-08-17 追加）

macOS ジョブは `.app` をビルドするだけで、**WKWebView を一度も実行して
いなかった**（前回の宿題 E / codex Q3）。シミュレータなら実機なしで本物の
iOS WebKit を動かせるので、そこまで進めた。

- `xcrun simctl` でシミュレータを起動し、
- `scripts/ruby-probe.html` を Safari で開いてスクリーンショットを撮り、
- アプリ本体も起動してスタート画面を撮る（WKWebView が立つかの確認）
- 画像は `ios-shots` アーティファクトに出る

**なぜアプリ本体ではなく専用ページなのか**: アプリはスタート画面のひと押しを
経ないとホームへ進まないが、`simctl` はタップを送れない。ルビの乗った画面まで
到達できないので、「iOS の WebKit がルビをどう組むか」だけを取り出した
ページを別に置いた。数値（ふりがなの実寸・行の高さ・ruby-position）は
**画面に文字として焼き込んである**——持ち帰れるのが画像だけだから。

手元（Windows）では検証できないので `continue-on-error: true`。落ちても
他のジョブを止めない。得たいのは合否ではなく成果物の画像。

> エンジン差の実測: ルビの乗る見出し行は WebKit 61px / Chromium 53px。
> ルビの見た目を Chromium だけで測ると iOS では詰まる。

### 「テストが人間より速い」型の落とし穴（2026-08-17）

i18n の張り替え後、スモークが15件落ちた。原因はアプリではなく**テストの速さ**。

スタート押下の直後 500ms は、ホームのタイルへのクリックがアプリ側で握りつぶ
される（`views/home.js` の `armStartInputGuard`。スタートのひと押しがそのまま
アクティビティまで届く事故を防ぐための、正しい挙動）。テストはこれまで別の
待ち合わせでたまたま時間を消費していて、ガードを抜けていた。待ち合わせを
速くした瞬間に、ガード内で押すようになって一斉に落ちた。

**「テストが落ちた＝アプリが壊れた」ではない。** ここでは失敗時の DOM を
吐かせて（view は home のまま、タイルは5枚とも並んでいる）、押下だけが
効いていないことを見てから原因にたどり着いた。推測で2回外している
（フォント読み込み・要素の差し替え）ので、実地で確かめる価値があった。

### E. CI で実機の代わりにならないもの

codex Q1 の指摘。CI が緑でも実機で壊れうる:

1. iOS の音声出力遅延（`outputLatency` は記録するだけで補正していない）
2. NeuroNode の実入力経路（HID / Switch Control）は未検証。
   さらに `rhythm.js` は入力の `source`（keyboard / pointer）を試行に保存して
   いないので、後から入力経路を分離できない
3. iPad からのCSV取り出し（Blob + `a[download]` が WKWebView で通るか）

codex Q3 の提案: **iOS Simulator で実際にアプリを起動する XCUITest を1本**。
いまの macOS ジョブは `.app` をビルドするだけで一度も WKWebView を実行していない。
ローカルで検証できない（macOS 無し）ので、足すなら `continue-on-error` の
独立ジョブが安全。
