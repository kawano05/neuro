# neuro リズムゲームからスロット型逐次停止課題への置換計画書

* **対象リポジトリ**：`kawano05/neuro`
* **作成日**：2026年8月20日
* **文書状態**：実装前計画案 Ver.0.1
* **想定ファイル名**：`docs/slot-game-replacement-plan.md`

---

## 1. 計画概要

本計画では、NeuroNode導入訓練アプリ「neuro」に実装されている利用者向けリズム課題を、スロットマシンのリール停止操作を応用した**単一スイッチ式の逐次停止課題**へ置き換える。

ただし、一般的なスロットゲームに見られる賭博的な報酬構造を導入するのではなく、以下の要素のみを訓練へ利用する。

* 動いている対象を見て、適切なタイミングで入力する
* 1回の入力で1本ずつリールを止める
* 複数回の入力を順番に完遂する
* 結果が揃うかどうかを見届ける期待感
* 入力結果が視覚的に分かりやすく残ること

利用者向け名称は「スロット」ではなく、**「えを とめる」「リールを とめる」「3つの えを そろえる」**など、賭博を連想させにくい名称を使用する。

現行システムは、シェル側で入力時刻を一元的に取得し、共通のゲームモジュール契約を通して各ゲームへ入力を渡す構造になっている。この基盤はスロット型課題にもそのまま利用できる。

一方、現行のリズム課題は聴覚キューに対する感覚運動同期を測る課題であり、スロット型課題は視覚刺激に対する停止タイミングを測る課題である。そのため、本変更は単なるテーマ変更ではなく、**測定パラダイムの変更**として扱う。

## 2. 基本方針

### 2.1 置換対象

第1段階では、次の2課題を置換する。

| 現行ゲーム       | 置換後       | 内容                      |
| ----------- | --------- | ----------------------- |
| `rhythm-l1` | `slot-l1` | 1本のリールを目標位置で止める基礎課題     |
| `rhythm-l2` | `slot-l2` | 3本のリールを1本ずつ順番に止める逐次入力課題 |

現行のリズムゲーム群は、`rhythm.js` の共通エンジンを用いて複数モードを生成している。

### 2.2 当面残す課題

以下は第1段階では削除しない。

| ゲーム            | 方針                | 理由                  |
| -------------- | ----------------- | ------------------- |
| `gonogo`       | 独立した聴覚反応抑制課題として残す | スロットとは測定対象が異なる      |
| `calibration`  | 支援者向けの測定機能として残す   | 過去データとの継続性を保つ       |
| `fishing`      | 現状維持              | 聴覚だけでも成立する主要な反応時間課題 |
| `crane`        | 現状維持              | 既存の視覚・走査選択課題        |
| `color-legacy` | 現状維持              | 最初の反応確認に利用できる       |

`calibration` で求めた聴覚入力の基準オフセットは、検証なしにスロットの視覚停止判定へ適用しない。聴覚刺激に対する遅延と視覚刺激に対する遅延を、同一の補正値として扱える根拠がないためである。

### 2.3 旧ゲームIDを再利用しない

`rhythm-l1` の表示と中身だけをスロットへ変更する方式は採用しない。

新しい課題には、必ず以下の新規識別子を付ける。

```text
gameId: slot-l1 / slot-l2
taskType: slot
protocolVersion: slot-v1
```

理由は、旧リズムデータと新スロットデータが同じゲームIDやCSVへ混在すると、異なる測定値が同一課題のデータとして扱われてしまうためである。

## 3. 目的

### 3.1 利用者向けの目的

* 単一スイッチで入力するタイミングを練習する
* 1回だけでなく、複数回の入力を順番に行う
* 入力後の結果が画面に残ることで、操作と結果の関係を理解しやすくする
* 一定回数の課題を最後まで完遂する経験を作る
* 絵柄が揃う可能性によって、課題への興味を維持する

### 3.2 支援者向けの目的

* 利用者が目標位置に対して早く押す傾向か、遅く押す傾向かを把握する
* 入力タイミングのばらつきを把握する
* 1本目、2本目、3本目で精度が変化するかを確認する
* 連続入力時の疲労、焦り、二重入力を観察する
* 練習前後で停止精度が改善したかを比較する

### 3.3 研究上の目的

スロット型課題を、単なる娯楽ゲームではなく、次の課題として位置づける。

> 単一スイッチを用いて、周期的に移動する視覚刺激を目標位置で逐次停止する視覚運動タイミング課題

現行の研究計画では、主要仮説を`fishing`の反応時間に置き、リズム課題の指標は副次評価項目として扱っている。現在の主要仮説を維持する場合、スロットへの変更は研究全体の主要評価項目を直接変更するものではないが、副次評価項目と研究説明は更新する必要がある。

## 4. ゲーム仕様

## 4.1 利用者向け名称

推奨名称は以下とする。

| 内部ID      | 利用者向け名称 | 説明                   |
| --------- | ------- | -------------------- |
| `slot-l1` | ひとつ とめる | おなじ えが まんなかに きたら おそう |
| `slot-l2` | 3つ とめる  | 3つの リールを じゅんばんに とめよう |

ホーム画面のカテゴリー名は、次のいずれかを使用する。

* 「リールを とめる」
* 「えを そろえる」
* 「タイミング」

研究文書とソースコードでは「スロット型逐次停止課題」と表記してよいが、利用者画面では「スロット」「大当たり」「ジャックポット」などの語を使用しない。

---

## 4.2 `slot-l1`：1リール停止課題

### 課題内容

1. 画面上部に目標となる絵柄を表示する
2. 1本のリールを一定速度で回転させる
3. 目標の絵柄が中央の停止線へ来たときに入力する
4. 入力時点の論理位置でリールを停止する
5. 規定回数終了後、自動的にリザルトへ移動する

### 暫定プロトコル

| 項目     |     初期案 |
| ------ | ------: |
| リール数   |       1 |
| 絵柄数    |       6 |
| 1周の時間  | 3,200ms |
| 試行数    |       8 |
| 目標絵柄   | 試行ごとに指定 |
| 目標出現回数 | 1周につき1回 |
| 最大待機   |      4周 |
| 測定単位   | 1入力を1試行 |

値は実装後の予備試験で確認し、実データ収集前に固定する。

---

## 4.3 `slot-l2`：3リール逐次停止課題

### 課題内容

1. 3本のリールを同時に回転させる
2. 画面上部に目標絵柄を表示する
3. 1回目の入力で左リールを止める
4. 2回目の入力で中央リールを止める
5. 3回目の入力で右リールを止める
6. 3本の判定後、次のラウンドへ進む
7. 規定ラウンド終了後、自動的にリザルトへ移動する

### 暫定プロトコル

| 項目       |       初期案 |
| -------- | --------: |
| リール数     |         3 |
| 絵柄数      |        各6 |
| 1周の時間    |   3,200ms |
| ラウンド数    |         4 |
| 総入力数     |        12 |
| リール間の速度差 | 測定モードではなし |
| 最大待機     | 1リールにつき4周 |

L1とL2で回転速度まで同時に変えると、「難しくなった原因」がリール数なのか速度なのか区別できない。そのため、測定モードでは同じ速度を用い、L2では**逐次入力の増加だけ**を難度軸とする。

---

## 4.4 入力と停止処理

入力時刻は、現行ゲームと同じくゲーム内部で取得せず、シェル側の入力ファネルが取得した時刻を使用する。

```text
キーボード・タップ・NeuroNode入力
        ↓
シェルで performance.now() を取得
        ↓
gameHost
        ↓
slot.handleInput(inputTimestamp, source)
```

リールの見た目は`requestAnimationFrame`で描画するが、判定はフレーム位置ではなく経過時間から計算する。

入力された瞬間に論理上の停止位置を確定し、その後の減速アニメーションは、確定済みの停止位置へ見た目を追従させるだけとする。

これにより、iPadの描画負荷やフレーム落ちによって判定結果が変化することを防ぐ。

### 判定計算の基本形

```text
symbolIntervalMs = cycleMs / symbolCount

signedErrorMs
  = 入力時刻 - 最も近い目標絵柄の中央通過時刻
```

* 負の値：目標より早い入力
* 正の値：目標より遅い入力
* 絶対値が許容範囲以内：成功
* 許容範囲外：ずれ
* 最大待機を超えた場合：タイムアウト

## 5. 測定項目

### 5.1 主要な課題内指標

| 指標                      | 内容                 |
| ----------------------- | ------------------ |
| `medianAbsoluteErrorMs` | 目標位置からの絶対ずれの中央値    |
| `meanSignedErrorMs`     | 早押し・遅押し傾向を表す符号付き平均 |
| `sdSignedErrorMs`       | 入力タイミングのばらつき       |
| `hitRate`               | 許容範囲内で停止できた割合      |
| `completionTimeMs`      | セッション開始から終了までの時間   |
| `extraInputCount`       | 入力受付外の追加入力数        |
| `timeoutCount`          | 最大待機を超えた回数         |
| `meanObservedCycles`    | 入力までに見送った平均周回数     |

### 5.2 L2固有の指標

* リール位置別の誤差

  * 左リール
  * 中央リール
  * 右リール
* 1本目から3本目にかけての誤差変化
* リール間入力間隔
* 二重入力の発生回数
* 3本すべて成功したラウンド数
* 少なくとも1本成功したラウンド数

### 5.3 結果表示

#### 利用者向け

* 「3つのうち 2つ とめられた」
* 「さいごまで できました」
* 停止した絵柄の並び
* 穏やかな完了音
* 「もういちど」「メニューへ」

#### 支援者向け

* 成功率
* 絶対ずれ中央値
* 早め・遅めの傾向
* ばらつき
* 各リールの停止精度
* タイムアウト数
* 追加入力数

利用者向け画面では、失敗を大きく強調しない。支援者向けの数値と利用者向けのフィードバックを分離する。

## 6. ランダム性の扱い

### 6.1 測定モード

測定モードでは、再現できない完全ランダムな出題を使用しない。

* 固定シードまたは事前作成した出題セットを使用する
* リールの絵柄順を記録する
* 初期位相を記録する
* 目標絵柄を記録する
* エンジンバージョンを記録する
* 同じ条件を再現できるようにする

### 6.2 練習モード

練習モードでは、絵柄順や目標絵柄をランダムにしてよい。

ただし、入力後に乱数で成功・失敗を変更してはならない。結果は必ず利用者の入力時刻によって決まるものとする。

### 6.3 許可する演出上の変化

課題完了後、すべての利用者に同程度で提示される次の演出は許可する。

* 完了時の背景模様の変化
* 数種類の完了音からの選択
* キャラクターや図形の表示
* 控えめな紙吹雪
* 揃った絵柄に応じた短いアニメーション

これらは、再試行回数や低確率の大当たりに連動させない。

## 7. 倫理・モラル上の設計要件

### 7.1 導入しない要素

以下は明確に非スコープとする。

* 金銭、コイン、メダル、掛け金
* 払い戻し率
* 7、BARなどのカジノ固有記号
* ジャックポット
* 連勝ボーナス
* ログインボーナス
* 課金
* ランキング
* 損失を取り返す仕組み
* 回数を重ねるほど当たりやすくなる仕組み
* 低確率の大当たりだけを極端に豪華にする演出
* 終了条件のない無限プレイ
* 「あと1回」を強く促す継続誘導

### 7.2 近接失敗の扱い

利用者の入力によって、目標の隣の絵柄で止まること自体は自然に発生する。

ただし、次の処理は行わない。

* 目標の一つ手前へ意図的に停止位置をずらす
* 「おしい！」を通常の失敗より派手に表示する
* 近接失敗の直後だけ再試行を促す
* 目標の隣で止まる確率を意図的に増やす

自然に発生した近接失敗は、通常のずれとして記録する。

### 7.3 固定終了

各セッションは規定回数で必ず終了させる。

終了後は既存のリザルト画面へ移動し、「もういちど」と「メニューへ」を同じ優先度で提示する。再試行を初期選択に固定しない。

### 7.4 研究文書での表現

研究計画書や卒論では、「射幸心を利用する」とは記載しない。

推奨する説明は以下とする。

> 結果への期待感と視覚的フィードバックを利用し、単一スイッチによる逐次停止課題への参加意欲を高める。

これは用語を言い換えて隠すためではなく、実装自体を賭博的な可変報酬から分離した上で、その機能を正確に説明するための表現である。

## 8. アクセシビリティ要件

スロット型課題は、現行リズム課題と異なり画面注視を必要とする。そのため、次の対応を必須とする。

* `visualRequired: true`を設定する
* `hideVisualTasks`が有効な場合はホームに表示しない
* スロットカテゴリー内に選択可能な課題がなくなる場合、カテゴリー自体を表示しない
* 絵柄を色だけで区別しない
* 輪郭と形状の異なる絵柄を使用する
* 高コントラスト設定に対応する
* 停止線を太く、常時表示する
* リールの回転方向を統一する
* 背景と絵柄を同時に激しく動かさない
* 完了演出では`prefers-reduced-motion`を尊重する
* 点滅演出を使用しない
* 支援者が常に中止できる
* 中止時にも直前までの試行データを保存する

スロット課題を非表示にしても、聴覚中心の`fishing`などが利用できる状態を維持する。

## 10. 状態保存と移行

### 10.1 ストレージバージョン

保存スキーマを次へ更新する。

```text
neuronode-prototype-state-v3
    ↓
neuronode-prototype-state-v4
```

### 10.2 移行方針

* v3に保存された既存設定をv4へ移行する
* 既存の`taskType: sms`セッションをそのまま保持する
* 旧リズムセッションをスロットセッションへ変換しない
* 旧リズム設定は少なくとも1バージョン保持する
* 旧ゲームコードはデータ移行とCSV出力確認が完了するまで削除しない
* v4保存失敗時もv3データを削除しない
* セッション数上限は既存の`MAX_SESSIONS`を継承する
* 不正なスロット試行を個別に除外するサニタイズ処理を追加する
* 試行欠落が発生した完了セッションは、完了扱いのままにしない

### 10.3 データ収集開始後の扱い

すでにリズム課題の本番データを収集している場合は、変更日を境にプロトコルを分ける。

```text
旧条件：rhythm-v1
新条件：slot-v1
```

両者を同一課題の前後比較として扱わない。

## 12. 実装フェーズ

### P0：研究・仕様の固定

## 15. 主なリスクと対策

| リスク       | 内容                            | 対策                                             |
| --------- | ----------------------------- | ---------------------------------------------- |
| 研究目的の不整合  | 聴覚同期課題を視覚停止課題へ変えるため、旧説明が成立しない | 新taskTypeと新プロトコルを定義し、研究文書を更新する                 |
| 旧データとの混在  | 同じIDを使うと異なる課題が同じデータとして扱われる    | `slot-l1`、`slot-l2`を新規IDとして追加する                |
| 視覚依存の増加   | 画面注視が難しい利用者には利用できない           | `visualRequired`と`hideVisualTasks`を設定し、聴覚課題を残す |
| フレーム落ち    | 描画性能によって停止位置がずれる              | 論理位置を入力時刻から計算する                                |
| 二重入力      | 1回の操作で複数リールが停止する              | 入力ロックとイベント系列の消費処理を実装する                         |
| 難度過多      | 絵柄や速度によって成立しない                | L1を1リールにし、予備試験後に固定する                           |
| 賭博表現への懸念  | 支援アプリとして不適切に見える               | 利用者向け名称、素材、報酬構造を非賭博型にする                        |
| 継続誘導の過剰化  | 終了しにくい設計になる                   | 固定試行数、自動終了、対等な終了導線を採用する                        |
| 揃わなさによる失望 | 失敗が強調される                      | 完遂を評価し、揃った数は中立的に表示する                           |
| PWAキャッシュ  | 更新後も旧リズム画面が残る                 | Service Worker更新とPWA競合テストを実施する                 |

## 17. 最終方針

最初の実装では、既存のリズム系全体を一度に削除するのではなく、次の構成とする。

```text
利用者ホーム
├─ いろと おと
├─ リールを とめる
│  ├─ ひとつ とめる       slot-l1
│  └─ 3つ とめる          slot-l2
├─ アームを とめる
├─ さかなつり
├─ おとの はんのう        gonogo
└─ まなぶ・つたえる

支援者向け設定
└─ そくてい               calibration
```

この構成であれば、スロット特有の「動いているものを止める楽しさ」と「結果が揃うかを見る期待感」を利用しながら、賭博的な報酬設計を避けられる。

また、スロットを新しい視覚タイミング課題として独立させることで、旧リズム課題のデータ互換性を保ち、卒業研究においても変更内容と測定対象を明確に説明できる。
