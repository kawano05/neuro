## 2. 確定した観察事実

### 2.1 走査

- 0:08前後の抽出画像では、アプリの黄色い走査フォーカスと、右ペイン全体を囲む青い枠が同時に見える。
- ユーザーの実機操作でも、iPad側Switch Controlとアプリ側走査の競合が報告された。
- `src/lib/scan.js:7-12` は、iOS実機のSwitch Controlと自前走査が二重走査になることを既知制約として明記している。
- `src/lib/state.js:69-71` では `autoScan: true` が既定値で、iOS時に自動OFFへ切り替える実装はない。
- `src/lib/scan.js:62-68` とゲーム画面のCSSにより、アプリの自前走査はゲーム中には停止・非表示になる。競合の主戦場はホーム、結果、設定などのシェル画面である。
- `src/lib/scan.js:45-50` は走査対象ごとに `scrollIntoView()` を実行するため、二重走査時には画面の自動移動が競合を悪化させうる。

### 2.2 音声

- 録画上の発話・合図はおよそ `-10 dBFS`まで達し、疎な区間の平均はおよそ `-35〜-42 dBFS`。実機スピーカーの音圧ではなく、録画ファイル上のデジタルレベルである。
- `src/lib/audio.js:205-214` のTTSは `rate = 0.92` のみ指定し、`volume` は未指定、すなわち既定値のまま。
- 合図音・効果音には `0.05`、`0.04` などの小さい上限がある。TTSとWeb Audioの相対差は大きい。
- アプリTTSは次の発話前に `cancel()` され、ゲーム開始時には `stopSpeech()` されるため、アプリ内TTS同士の無制限な重複には対策がある。
- 一方、`src/lib/games/colorLegacy.js:44-49` では押下ごとに純音とTTSを同時に出す。OS読み上げ、live region、アプリTTS、Web Audioは別経路であり、全経路を横断する排他制御はない。

### 2.3 終盤の無音

- `593.821655〜718.500952秒`、約`124.679秒`は録画上のデジタル無音。
- 無音開始直後には「色と音」からホームへ戻り、以後は黄色い自前走査がホーム項目を周回している。
- `scan.js` の走査ステップはフォーカスクラスとスクロールだけを更新し、音や読み上げを出さない。
- したがって、この録画だけから「音声エンジンが故障した」とする証拠はない。現在のホーム走査が無音設計であることと整合する。

### 2.4 ゲーム間の差

- UFOキャッチャーと釣りは、イラスト、進行、成功・失敗の演出、得点、結果表示が多層化されている。
- リズムは短い純音差と短いフラッシュ、結果の割合・時間差が中心。
- 色と音は色円、純音、タイトル読み上げが中心で、規定試行数や結果画面がない。
- 差は画風だけでなく「押した結果がどの経路で届くか」というフィードバック契約の差でもある。
- ただし、リズムの `measure` / calibration と釣りの測定刺激には、次の刺激を
  覆わないという制約がある。この制約を練習版の見た目を簡素にする理由へ広げない。

### 2.5 未保存警告

- 左ペインの赤い「変更が保存されていません」は録画中ほぼ常駐する。
- この文字列はNEURONODEリポジトリ内に存在しない。左ペインのニューロノードコントローラー側の状態であり、NEURONODEの保存失敗ではない。
- ただし、しきい値などが未保存ならセッション再現性に影響するため、運用上の記録対象にはなる。

## 3. Claudeの主な反論（2026-08-18時点）

1. 終盤無音は故障よりも、無操作のホーム走査に音がない設計で説明できる。
2. 二重走査はコード上の既知制約だが、動画中の青枠だけではiOS Switch Controlと100%断定できない。古い `.scan-focus` が残った可能性も排除できない。
3. 読み上げ問題の中心はアプリTTS同士の重複より、TTSと小さい合図音・効果音の音量格差である。
4. 測定版の刺激保護は必要だが、練習版のゲーム性を抑える理由にはならない。
   練習と測定を表示モードで分け、測定だけ予告キューを切る。
5. 未保存警告は別アプリの問題であり、NEURONODEの修正項目へ直接入れるべきではない。

Claudeが提案した追加案:

- iOS Switch Controlモードで `autoScan=false` と走査UI非表示。
- 任意の走査ティック音と、長時間無操作時の状態案内。
- リズム・色と音をゲーム別の世界観、進捗、事後結果まで作り込む。
- コントローラー設定の保存を開始前チェックへ追加。

## 4. Grokの主な反論（2026-08-18時点）

1. 言えるのは「実機シェルで自前走査がON」「iOS運用プロトコルと不一致」「一部フレームに黄枠と青枠が共存」の三点。ゲーム中の自前走査は止まっている。
2. 終盤無音はホーム走査・退出で説明でき、AudioContext故障とみなす根拠は薄い。
3. 問題は単純な音量ではなく、TTS、Web Audio、OS読み上げ、live regionの所有権が統一されていないこと。
4. 測定へ予告演出を持ち込むと前提を壊すが、練習は本格的なゲーム版面にできる。
   結果・進捗・操作の契約に加え、見た目の完成度も全ゲームで製品水準へ揃える。
5. 未保存警告はコントローラーの運用問題。未保存しきい値を使ったセッションは再現条件が不足する。
6. Split Viewではホーム項目数とページ分割が変化して見えるため、フルスクリーンとの差を試験すべき。

Grokが提案した追加案:

- 測定中はTTS禁止、測定後は結果通知を共通化する契約。
- 色と音では純音と長いタイトル読み上げを同時に出さない。
- Split Viewとフルスクリーンを別条件として固定。
- サイレントスイッチと `AVAudioSession` の実機確認。

## 6. 合意した優先順位

### P0: シェル画面の走査所有者を一つにする

- iPad Switch Control運用時は、アプリ自前走査をOFFにし、走査ドックを非表示にする。
- まずは自動検知でなく、明示的な「iPad Switch Controlモード」でよい。
- OS走査へ委譲した状態で、全シェル項目へ到達できるか確認する。
- ゲーム中は現行どおり自前走査を止め、測定入力はHID Spaceまたは画面タップなど、実験プロトコルで定めた経路を使う。

### P1: 音声の所有権と相対音量を整理する

- OS読み上げON/OFF × アプリTTS ON/OFFの2×2で、どの声が大きいかを確定する。
- iPad Switch Controlモードでは、アプリTTSを既定OFFまたは低音量にする候補を試す。
- 色と音では純音と長いTTSを同時に出さない。
- 合図音・効果音を一律に上げず、まずTTS側の音量とタイミングを調整する。

### P2: 見た目の完成度を揃え、練習と測定を分離する

- 色と音、リズムL1/L2、たかいおとだけは、背景、主役、世界内進捗、成功・失敗、
  蓄積報酬、同じ世界のリザルトまでゲーム別に作り込む。中央円＋説明文を既定へ戻さない。
- rhythm の practice は、ゲーム別テーマと判定面へ流れる予告ノートを許可する。
  予告を使った回は `visualGuidance=true` として記録し、聴覚のみの測定へ混ぜない。
- `measure` と calibration は予告ノート、拍前パルス、次の音種の事前表示を禁止する。
  ただし無地にせず、暗色グリッド、静止判定線、24目盛り、入力後マーカー、
  計器盤型リザルトを備えた完成された精密機器として描く。
- 結果画面は数値の意味、要約、`もういちど → メニューへ` の順だけを共通化し、
  背景・見出し・獲得物はゲーム固有の世界観を継続する。
- **走査**: ゲーム中はステージ全体だけを入力面とし、装飾は走査・フォーカス対象外。
  レディ／リザルトの操作順を固定し、全操作標的を44×44 CSS px以上にする。
- **reduced-motion**: 連続スクロール、パララックス、粒子を止め、固定ノート枠、
  輪郭切替、事後スタンプ、静止背景の段階差へ置換する。世界観ごと消さない。
- **high-contrast**: 文字4.5:1、主要な非文字UI 3:1以上、輪郭4px以上を満たし、
  色だけでなく形・数字・短い文字を併用する。
- **844×390横向き**: 進捗、主操作面、判定面、終了、リザルトCTAを重ねず、
  44px標的を維持する。装飾を先に縮退し、横スクロールを発生させない。

## 8. 最終結論

今回の主要不具合は、ゲーム中ではなく**シェル画面でiPad Switch Controlとアプリ自前走査を同時に動かしたこと**である。修正の第一歩は枠を同期させることではなく、走査所有者を排他的に選ぶこと。

読み上げは、アプリTTSの相対音量が大きい可能性と、OS音声を含む複数経路の重複可能性を分けて扱う。先にTTSを下げる・重ねない方向を試し、測定合図を一律に大きくしない。

終盤の約125秒無音は、現在の証拠では音声故障ではなく、音を出さないホーム走査と退出で説明できる。別途、走査中に聴覚手がかりを追加するかは、走査排他と音声整理の後に利用者テストで決める。

ゲーム品質はフィードバック契約だけでは足りない。各ゲーム固有の見た目を結果まで完成させ、
practice は本格的なゲームとして作る。測定妥当性は `measure` / calibration の
予告を切ることで守り、簡素な中央円へ戻す理由にはしない。
