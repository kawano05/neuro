# デザイン改修（はっきりした色）— 要望の整理と判断（2026-09-25）

ブランチ `design/hakkiri` で行っている、利用者の世界（スタート〜ホーム〜ゲーム〜
けっか）の見た目の作り直しの記録。**何を直したか**より、**なぜそう判断したか**と
**まだ何が残っているか**を残す（引き継ぎ書 `handoff-2026-08-17.md` と同じ流儀）。

入力は2つ:

- クライアントとの打ち合わせ動画（約53分）。前半15分で現行アプリを画面共有し、
  残りは口頭での議論。音声はローカルで文字起こしして読んだ（外部サービスには渡していない）。
- デザイン案 `nuro-design-hakkiri.html`（1180×820 のモックアップ7画面）。

> 動画・文字起こしには個人名や学校の情報が含まれるため、リポジトリには入れない。
> ここに書くのは、画面の要件として必要な内容だけ。

## 1. 打ち合わせで出た要望

括弧内は動画の時刻。

### 1.1 全体の方向

- **技術や機能はそのままでよく、問題はデザイン。**（13:13）
  機能自体は褒められている。いまの見た目は大人っぽく、
  支援者向けの画面に見える。（10:48, 11:23）
- 利用者は NeuroNode を使う重度の方で、何をやっても「初めての経験」になる。
  認知面は幼い子どもを想定してよく、**子ども向けと思われてもいい**。
  年齢に関係なく、みんなが楽しめる形にする。（9:56, 32:53, 34:14）
- 伝える相手は、機械が得意でないお母さん、作業療法士、学校の先生。
  「無理、難しい」と思われた時点で使われなくなる。（12:09）
- 目的は、市販のコミュニケーションアプリへ進むための**最初の練習**。（34:28）

### 1.2 画面の流れ

- スタート画面に小さく「せってい」があるので、**先に設定しないといけないと思った**。
  iPad のスイッチコントロールとアプリ側の設定の関係も、説明を聞くまで分からなかった。
  （4:59, 20:33）
- **ボタンはできるだけ少なく**する。表の画面は「はじめる」しかない、くらいでよい。（21:13）
- 画面の移動（ページめくり）は極力少なくする。何回も押す必要がある画面は、
  面倒で、それが「難しい」につながる。（38:59）
- 「走査停止」のような言葉は、普段目にしないので難しく感じる。（7:29）

### 1.3 メニュー（ホーム）

- 遊びは**絵のサムネイルで、1画面にすべて並べる**。次のページへ送らない。（11:48, 38:05）
- **いちばん簡単なものを左上、いちばん難しいものを右下**に置く。（38:25）
- どれから始めればよいのか、どれが難しいのかが分からなかった。
  **難しさを枠の中に書く**（かんたん／すこし むずかしい など）。（5:37, 6:52）
- 設定は支援者しか触らないので、**端に小さく**置く。走査で選べなくてよい。（23:55）

### 1.4 はじめの遊び（失敗のない遊び）

- 真っ暗な画面から、**押すと絵がポンと出てくる**だけでよい。イルカが出て消え、
  次は亀、次はバナナ……のように。言葉の説明はいらない。（9:12〜10:22）
- 力を入れたら画面が反応する、だけのものがまず要る。NeuroNode では「押した」
  感覚そのものが無いので、何をしたら何が起きたのかが最初は分からない。（21:49）
- **失敗がほぼ無く、やったことが全部プラスになる遊び**を増やしてほしい。
  利用者は自分でできた経験が少ない。（18:26）
  例: 風船が押すたびに割れる、塗り絵の絵がだんだん現れる。時間制限は無くてよい。
- 現行の「色と音」は、機能はそのままで絵を変えれば、最初の遊びとして使える。（11:04）

### 1.5 タイミングの遊び（リール・さかなつり・アーム）

- 仕様はいまのままでよい（速さを変えられる）。**絵を変える**くらいでよい。（20:06）
- リール: 枠を大きく、周りの余計なものは要らない。止まったときに
  「当たった」と分かる派手な演出がほしい。間違えたときはへこませず、
  あっさり次へ。いまの前向きな言葉（もう一回がんばろう）は良い。（14:30〜15:58）
- さかなつり: アタリのときに**大きなビックリマーク**が出れば、押す時だと分かる。
  いまは下に小さく「アタリ」と出るだけで気づきにくい。（17:24〜18:09）

### 1.6 けっか

- 「おわりました」は硬い。「できた」でよい。**最小限の情報**で、
  点数と「よくできました」「きみはプロだ」のような一言でよい。（16:44〜17:19）

### 1.7 音

- 音はとても大事。画面を見られない・顔を向けられない利用者にも届く。
  読み上げより、効果音（ボカーン、ボヨーン）のほうが反応がよい。（34:56〜35:49）
- ただし**強すぎる音ばかりだと発作を起こす人もいる**。楽器の心地よい音から
  びっくりする音まで、**遊びごとに選べる**ようにしてほしい。（36:18〜37:21）
- できたときに**笑い声や「やったー」**が入ると、周りが家族だけでも盛り上がる。（46:15）

### 1.8 設定

- 設定機能そのものは残してほしい。（23:31）
- 遊んでいる最中に「速いね」と思ったら、**その場で変えたい**。ホームへ戻るのが
  手間。**各ゲームの中に、支援者だけが触る設定ボタン**を置く。（26:21〜28:46）
- 設定の言葉が難しい。**小学校高学年が読んで分かる**くらいに。
  研究者向け（測定）の項目は分けたほうがよい。（28:52〜29:47）
- 最初の画面だけでよいので、支援者向けの簡単な説明書があるとよい。（24:41）
  自分で作って、ご家族に渡すつもりだった。（25:05）

### 1.9 参考に出た遊び

- 「誰でも野球盤」: クリックだけでバットを振ってボールが飛ぶ。これをアプリの中に
  入れておいてもいい。PK戦（サッカー）版があってもいい。（43:16〜44:09）
- 展示会ではダーツ（ボールを飛ばして貼りつく）がいちばん人気だった。大人も遊ぶ。（32:02）
- 設定の中でボールの大きさをその場で変えられるソフトが使いやすい。（28:11）

## 2. デザイン案の判定

**方向は合っている。そのまま実装できない点と、要望から漏れている点がある。**
直してから実装した。

### 2.1 要望に合っている点（採用）

| 要望 | 案での扱い |
|---|---|
| 表の画面は「はじめる」だけ | 絵＋「おして、はじめよう。」＋「はじめる」。せっていリンクを消した |
| 絵のサムネイルを1画面に、簡単→難しいの順 | 大きな1番（左上）から5番（右下）までのグリッド |
| 難しさを枠の中に | 「はじめては ここ」「なれたら」「チャレンジ」の札と①〜⑤の番号 |
| はっきりした色 | 遊びごとに色を分け、カラーユニバーサルデザインの推奨配色を使用 |
| 設定は端に小さく、走査の外 | 右上の「支援者の設定」。走査対象にしていない |
| 真っ暗な画面から絵が出る | 「おすと でてくる」（黒地に動物が出る。5回で終わり、失敗なし） |
| 最小限のけっか | 「できた！ たのしかったね」＋出てきた動物＋2つのボタン |
| ゲームの中の設定 | 遊びの上部に「この遊びの設定」。背景・押したときの音・声を選べる |
| 音を選べる | 楽器の音／明るい効果音／なし |

### 2.2 そのままでは採れない点（直した）

| 案の内容 | 問題 | 直し方 |

| 「高い音」「絵」「遊び」などに**ふりがなが無い** | 利用者向けの文字は総ルビ（`i18n.js`）が既存の決まり。テストもある | 文言は全部 i18n を通し、ルビを付けた |

## 3. 判断の理由

### 3.1 「年齢中立」をやめた

詳細設計 §2.3 は、ホームを「年齢中立のアクティビティ」として作ると決めていた。
今回それをやめ、利用者の世界は**子ども向けに見えてよい**側へ振った。
クライアントが明言しており（1.1）、年齢中立の見た目が「大人っぽくて難しそう」に
見えていた、というのが打ち合わせで分かったこと。

支援者の世界（設定・評価ログ）は業務画面のまま。こちらは「分かりにくい」とは
言われたが、「子どもっぽくしてほしい」とは言われていない。

### 3.2 時間で進む遊びの設定は「はじめから」にする

「その場で速さを変えたい」（1.8）に対して、リール・アームのように**時間で進む
遊びは、設定を変えたら その回を中断して、はじめからやり直す**ようにした。

1回の記録（セッション）は1つの条件で行われたことが前提になっている
（`session.config` に速さを書き、解析で束ねる）。途中で速さが変わると、
その回がどちらの条件の記録なのか書けない。中断した回は `aborted` で残るので、
記録は失われない。

回数だけで進む「おすと でてくる」は、変えてもそのまま続ける（数えた回数は残る）。

### 3.3 そくていの回は見た目も変えない

さかなつりの大きな「！」やリールの当たり演出は、**れんしゅうの回だけ**に出す。
そくていの回（`difficultyMode: "measure"`）は、刺激の見え方を含めて固定のまま。

大きな「！」はアタリ音と同じ瞬間に出るので、目立ち方が変わると反応時間が
変わりうる。解析は「まず measure の回だけを見る」前提（引き継ぎ書 §2）なので、
れんしゅうの回に足すぶんには、測定の比較可能性を壊さない。

### 3.4 メダルは出さない

「当たったらメダルがパーンと出る」（1.5）は、リールの遊びでは**スロットの払い出し**
に見える。この遊びは賭博の表現を使わないと決めてある（詳細設計 §0A.5、README）。
当たりの演出は星と花丸にした。けっか画面の「メダル」も同じ理由で星にしている。

### 3.5 画面のスイッチ（ドック）を既定で出さない

利用者の画面の下にあった「走査停止」「入力」の2つは、打ち合わせで名指しされた
「分からない言葉」と「余計なボタン」だった（1.2）。

- NeuroNode・キーボードのスイッチは、ドックが無くても使える（押せば決まる）。
- 画面を直接さわる人は、タイルを直接押せる。
- 画面のどこを押しても「いまの枠を決める」使い方（狙って押せない人の画面スイッチ）は
  **設定で「画面に おすボタンを 出す」をONにしたときだけ**出す。

「走査停止」は利用者の輪から外した。走査を止めたいのは支援者で、
設定画面の「自動で うごかす」がその役をする。

### 3.6 iPad ではページに分けない

ホームのページ分割（`scanPaging.js`）は、画面の高さ 740px 以下を先読みで分けていた。
横長の画面（ノートPCのブラウザなど）では、グリッドにすれば6つとも1画面に入るのに、
先読みがページに分けてしまう（打ち合わせの画面共有で実際に「次のページ」が出ていた）。
グリッドで並べる画面では先読みをやめ、**描いてからはみ出したときだけ**分ける。
スマホの縦画面など、本当に入らない画面では従来どおり分かれる。

### 3.7 はじめの遊びを3つにした（2巡目）

打ち合わせの例（1.4）をそのまま遊びにした。どれも**失敗が無く、時間制限も無く、
5回押せば終わる**（`games/beginnerKit.js` の `BEGINNER_TARGET_PRESSES`）。

- 「ふうせん わり」: 5つのふうせんが、押すたびに1つずつ割れる。割れたところには
  そのふうせんの色の「パン」の印が残る。何回押したかがそのまま見え、並びも空かない。
- 「ぬりえ」: 線だけの絵に、押すたびに色が1か所ずつつく。**最後のひと押しで
  背景の丸ときらきらに色がつく**ようにして、「できあがった」がいちばん大きく
  変わる瞬間を最後に置いた。絵は「おすと でてくる」の動物を回ごとに替える。

ホームでは「おすと でてくる」を①、この2つを②③（札は「かんたん」）に置き、
①〜⑦で簡単→難しいの順を保つ。「学ぶ・伝える」は難しさの段に入らないので、
番号を出さず枠を破線にして分けた。

3つとも**測定の課題ではない**（`taskType` なし）。研究用の記録（session）は作らず、
押した回数だけを操作ログ（`switch`）に残す——「おすと でてくる」と同じ扱い。
記録の列は増えない。

### 3.8 音は遊びごとに選ぶ。びっくりする音は既定にしない（2巡目）

「強い音ばかりだと発作を起こす人もいる。遊びごとに選べるように」（1.7）に合わせて、
見え方と音の設定を遊びごとに持つようにした（`settings.playPrefs.<遊び>`）。
1巡目の `popBackground` / `popSound` / `popCheer` は、このブランチの中だけにあった
（本番に出ていない）ので、移し替えずに置き換えた。

- 選べる音: 楽器の音／明るい効果音／**びっくりする音**／なし。
- びっくりする音（低い「ドーン」）は、どの遊びでも**既定にしない**。選んだ時点で
  「音に驚きやすい人や、発作のある人には使わないでください」と出す。
- 音量は、ほかの効果音と同じ上限（`EFFECT_GAIN_CEILING`）の中。大きくするのではなく、
  音色で驚かせる。
- できたときの拍手と「やったー」は、あり／なし。拍手は雑音を合成した効果音なので、
  「効果音」を切ると出ない。「やったー」は読み上げなので、「読み上げ」を切ると出ない。
  笑い声は合成ではそれらしくならないので入れていない（録音素材待ち）。

### 3.9 設定画面の言葉（2巡目）

「小学校高学年が読んで分かる」（1.8）を目安に、支援者の設定画面の見出しと説明を
書き直した。例: 「走査間隔」→「枠が動く速さ」、「自動走査」→「枠を自動で動かす」、
「iPad Switch Controlモード」→「iPad のスイッチコントロールを使う」、
「視覚課題を隠す」→「画面をよく見る遊びを隠す」、「高コントラスト」→「くっきり表示」。
研究者向けのタブは「そくてい（研究）」と名前に書いた。

変えたのは**画面に出る言葉だけ**。設定の id・`data-settings-tab` の値・保存の形は
そのまま（保存済みの設定とテストがこれに頼っている）。支援者の画面の上に出る
走査の状態（「走査停止中」など）も、テストが文字で見ているので今回は変えていない。

### 3.10 リールは、れんしゅうの回だけ大きく、当たりを派手に（3巡目）

「この枠が大きいといい」「でかくバーンと流れていく感じ」「当たったらメダルがパーン」
（1.5）に対して、**れんしゅうの回だけ**リールの1コマを画面の高さに合わせて大きくし
（94px → 最大 136px。停止線もコマの高さから引く）、目標の絵で止めたときに星と
「ぴったり！」と明るい和音（ソ・シ・レ）を出すようにした。

- 大きさは刺激の条件なので、`SLOT_ENGINE_VERSION` を 3 に上げた（2 はリールが空に
  見える不具合の修正、§6）。れんしゅうとそくていのどちらの回かは `difficultyMode` で
  分かり、そくていの回の見え方と音は 2 と同じ。
- **メダルは出さない**（§3.4）。加えて、App Store の年齢区分の質問に「ギャンブルを
  模した表現（Simulated Gambling）」があり、リールからメダルが出る演出はそれに数え
  られうる。子ども向けの区分を保つためにも星にしてある。クライアントには一言伝える。

### 3.11 笑い声・生きものの声・ボヨーン（3巡目）

「笑い声みたいなのがあると、周りが家族だけでも盛り上がる」「ボカーン、ボヨーン」
「動物の鳴き声とか」（1.7）を入れた。録音は使わず合成で作り（`audio.js` の
`playLaugh` / `playBoing` / `playCreature`）、耳の代わりに次で確かめた:

- 描いた波形の山が、ほかの効果音と同じ上限（`EFFECT_GAIN_CEILING`）に収まること
  （`test-results/probe-sounds.mjs` で OfflineAudioContext に描いて測った）。
  2巡目の拍手は、ほかの効果音より約19dB小さかったので、このとき直した。
- 聴いて確かめられるよう、WAV に書き出して開発者へ送った。

合成の笑い声・鳴き声は、それらしさに限りがある。**`src/assets/sounds/` に録音を置けば
合成の代わりに鳴る**ようにしてある（`soundAssets.js`。名前は laugh / boing /
creature-dolphin など）。App Store に出す前に、使ってよい権利のある録音へ替えるとよい。

出てくる生きもの（イルカ・カメ・タコ・カニ・クジラ）のうち、鳴き声のあるイルカと
クジラは声らしく、無いものは動きの音（泡・にゅるん・チョキチョキ）にした。
できたときのおいわいは「拍手と笑い声／拍手／笑い声／なし」から選ぶ（既定は拍手と
笑い声）。「なし」以外は「やったー」の声も出る。

### 3.12 ボールを打つ遊び（3巡目）

「誰でも野球盤」（1.9）の形で「ボールを 打つ」を足した。ボールが転がってきて、
押すとバットを振る。**ボールが出ているあいだに振れば必ず当たり**、タイミングが
合うほど遠くへ飛ぶ（前後 0.12 秒でホームラン、0.3 秒までヒット、ほかはころころ）。
見送った球は数えずにもう一度投げ、構えているあいだの押しは素振りにする——
どの押しでも必ずバットが動き、失敗という結果が無い。

ホームでは、失敗の無い①〜③と、タイミングの遊び（リールから）のあいだの④に置いた。
タイミングが合うと「もっと飛ぶ」ことで、合わせる練習の入り口になる。測定の課題では
ない（`taskType` なし）ので、研究用の記録は作らない。展示会（HCR）で大勢に試して
もらう遊びとしても使える。

ロビーは9つになったので、横長の画面は4列×3段（1番を 2×2 で左上）、縦長は2列にした。
「学ぶ・伝える」は段の色から外し、灰色の帯と破線の枠にした（緑は野球へ）。

### 3.13 スマホでもページに分けない（3巡目）

スマホの幅では、画面の高さからの当て（740px 以下なら分ける）でホームをページに
分けていた。iPhone（Safari で 664px）では9つが3ページに分かれ、「ページを
めくらせない」（1.3）に反していた。ホームはどの幅でもグリッドなので、行の高さを
画面の残りに合わせて伸び縮みさせ、**描いたあとに入らなかったときだけ**分ける
ようにした。背の低いスマホでは案内の一言と1番の説明文を外し、余白を詰める。
iPhone SE を Safari で開いたとき（548px）のような、本当に入らない画面だけが分かれる。

### 3.14 「学ぶ・伝える」の中の画面も、利用者の見た目に（3巡目）

「マッチング」「VOCA」「文字学習」の3画面は、デザイン改修の前の業務画面のまま
だった: 英語の小見出し（Scan matching など）、「スキャン・マッチング教材」
「定型句VOCA」「文字学習ソフト」という名前、ふりがなの無い問い、色の四角に
「りんご」と書いただけの選択肢。打ち合わせで言われた「難しい言葉」「大人っぽい」
（1.1, 1.2）がそのまま残っていた。

- 名前を「どれかな？」「ことばで 伝える」「文字を えらぶ」にした（ホームのタイルと
  画面の見出しが同じ名前）。問い・ことば・分類にふりがなを付けた。
- 「どれかな？」の選択肢に絵を描いた（りんご・そら・はっぱ・ゆき・かたち・くつ・
  パン・ほん・いす）。「学ぶ・伝える」の中の3つのタイルの絵も描き分けた（前は3つとも同じ絵）。
- 間違えたときの声は「おしい！ つぎも やってみよう」（前は「違います」）。
- **記録と流れは変えていない**。選んだ答え・ことばの記録（logEvent の label）は元の
  文字のまま、正誤ののち次の問題へ進むのも同じ。効果測定の手順（content.js の
  evaluationTasks、「VOCAで『痛いです』を選択」など）がこの画面と名前で数えるため。
  ふりがなは画面に出すときだけ付ける（content.js の PHRASE_RUBY、promptRuby）。

### 3.15 枠が動いたときの音（3巡目）

「画面を見なくても、音なら届く。顔を向けるのが難しい子もいる」（1.7）に対して、
支援者の設定の「スイッチ」に「枠が動いたときの音」（なし／小さな音／名前を読む）を
足した（`settings.scanFeedback`）。名前を読むと、黄色い枠が次へ動くたびにその項目の
名前を読み上げる——画面を見ずに、聞いて選べる（AAC の「聴覚走査」）。

- 既定は「なし」（今までと同じ）。使う人に合わせて支援者が入れる。
- 鳴らすのは枠が「動いた」ときだけ。画面を描き直したときにも鳴らすと、選んだ直後の
  「せいかい！」などの声を、次の項目の名前が打ち消してしまう。
- 利用者の画面でだけ鳴らす（支援者の画面では鳴らさない）。読み上げを切っているときは
  「名前を読む」でも小さな音になる。

### 3.16 タイミングの遊び4つ（リール・高い音だけ・アーム・さかなつり）（4巡目）

打ち合わせでは、この4つは「仕様はそのままでいい。イラストを変えるくらいで」
「かわいい感じ」「間違えたときも へこませず、あっさり次へ」「終わりました は硬い、
できた でいい」と言われた（1.5, 1.6, 1.4）。

- **見た目（れんしゅうの回だけ）**: 遊ぶもののまわり（台・枠・背景・飾り）だけを
  明るくした。リールは桃色の地に紫の枠、高い音だけは紫と黄の台（両脇のスピーカー・
  上のランプ・「ゲーム」の札・「0000」の桁そろえを外した）、アームは明るい地に茶色の
  台（ホームのタイルと同じ色）。**合図・目標・動くもの（リールの絵、音符、アームと
  景品、魚）は変えていない**。そくていの回は今までの見た目のまま（§3.3）。
  リールのれんしゅうの見た目は、まだ出していない版 3 の中に含めた（§3.10）。
- **言葉（どちらの回も）**: 外れたときの「逃げられた」「届かなかった」を「おしい！」
  「もう すこし！」に、終わりの声の「おわりました」を「できた！」にした（高い音だけの
  「達成率」も言わない）。リールで外したときは「おしい！」と出してすぐ次へ（れんしゅう
  だけ）。リールの「○本目」はやめた——「本」は数で読みが変わり（1本＝いっぽん）、
  ふりがな「ほん」が合わない。「のこり ○かい」「○ばんめ」にした。
- **さかなつりの「アタリが続く長さ」**（れんしゅうの回だけ。ながい 3秒／ふつう 2秒／
  みじかい 1.4秒、設定画面では 4秒も）: 4つのうち、さかなつりだけ遊びの中で何も変え
  られなかった。変えた値は試行ごとの limitMs と session.config に残り、CSV にも出る
  （もともと記録していた列）。セッション一覧の条件には、既定と違うときだけ
  「アタリ ○ms」と出す（既定の回は今までどおり同じ束で推移が続く）。

### 3.17 音と絵の見直し（5巡目）

**音の大きさ。** iPad の内蔵スピーカー相当（300Hz より下がほとんど出ない）で測ると、
効果音は読み上げの声より 17〜41dB 小さかった（楽器の音 −19、拍手 −26、笑い声 −31、
ボールを投げた「シュッ」−41。`test-results/probe-loudness.mjs`）。「できた！」で
拍手・笑い声と「やったー」が同時に鳴ると、声に隠れてほとんど聞こえない。
打ち合わせでは「読み上げより効果音のほうが反応がよい」と言われている（§1.7）。

- 効果音の上限（`EFFECT_GAIN_CEILING`）は「測定の合図を覆わない」ための決まりなので、
  **合図のある遊び（taskType あり）では何も変えない**。合図の無い場面（はじめの遊び・
  ボールを打つ・ホームや学ぶ画面）だけ、1音ごとの出口で 12dB 持ち上げる
  （`audio.js` の `effectOutputGain`、場面は gameHost が切り替える）。短い音・帯の狭い音は
  さらに音ごとに足して、どれも楽器の音と同じくらい（声より 6〜8dB 小さい）にそろえた。
- できたときは「歓声と拍手 → 笑い声 → やったー の声」の順にずらす（`beginnerKit.js`）。
- 「ボカーン」は音の大半が 300Hz より下で、iPad では 11dB 落ちてほとんど鳴らなかった。
  三角波の「ボ」と 1〜2kHz の「カーン」にした（驚かせるのは大きさでなく音色、は同じ）。
- スリープやほかのアプリのあと、音が止まったまま残ることがある（iOS）。操作のたびに
  確かめて戻す（`resumeIfSuspended`）。以前はスタート画面の最初のひと押しだけだった。
- 消音（マナーモード）で効果音だけ鳴らなくならないよう、Audio Session を「再生」に
  する（iOS 17 以降）。**アプリ版は、iOS のプロジェクトを作るときに、ネイティブ側でも
  `AVAudioSession` を `.playback` にする**（AppDelegate）。実機で確かめること。
- BGM は入れない。測定の遊びでは合図の音を聞くこと自体が課題で、押したときの音
  （自分がやった手応え）も BGM に埋もれる。強い音が続くことへの心配もある（§1.7）。

**録音の効果音。** 公開のリポジトリに置いてよい（再配布してよい）ライセンスの音だけを
選んだ（OtoLogic＝CC BY 4.0、Wikimedia Commons の CC0・CC BY）。効果音ラボは音が良いが
再配布禁止で、このリポジトリは公開なので使えない。`scripts/prepare-sounds.mjs` で短く
切り、頭の無音を削り、大きさをそろえる。クレジットは `src/lib/soundCredits.js` で、
設定「見え方・音」のいちばん下に出す（CC BY の条件）。測定の遊びの音は録音に替えない。
笑い声は、利用者側で聞いて別のものを選び直すことになった（合成のまま）。

**絵。** アイコンを、ホームの①（紺の地に水色のイルカと星）から作り直した
（`public/icon.svg`、PNG は `scripts/render-icons.mjs`。App Store 用の 1024px と起動画面は
`resources/`）。緑だった旧デザインの色（theme-color・manifest・起動の地）も白へ。
iPhone / iPad の「ホーム画面に追加」は SVG を使わないので、`apple-touch-icon.png` を足した。
さかなつりの船と魚は、iPad で 1.3〜1.6 倍に引き伸ばされてぼやけていたので、形と色は
変えずに2倍の細かさにした（`scripts/upscale-fishing-art.py`）。リールの絵の見本
（そくていの回だけ出る）は表示の5倍の大きさだったので縮め（673KB → 268KB）、使って
いないブランドのロゴ用の書体（約100KB）を外した。

### 3.18 読み上げ（5巡目）

利用者側から「日本語も英語も、読み上げがあまりにもたどたどしい」と言われた。
原因は3つあった。

1. **画面の分かち書きをそのまま声に渡していた。** 空白のたびに声が切れる。声に渡す
   ときだけ、日本語の字どうしのあいだの空白を外す（`i18n.js` の `toSpeechText`）。
   題名と説明のように文をつなぐときは句点を足す（`joinSpeech`。足さないと
   「アームでつかむアームが…」と1語のようにつながる）。
2. **数のあとの助数詞がかなだった。** 読み上げは「1かい」を「いちかい」、「3ひき」を
   「さんひき」と読む。画面では読みが数で変わる字（匹・本）に一つのふりがなを
   付けられないのでかなのままにし、声に渡すときだけ漢字へ戻す。
3. **声を選んでいなかった。** iPhone / iPad は、声を指定しないと機械的な声
   （Eloquence の Eddy・Flo… や、おもちゃの声）になることがある。その言語の声から、
   端末の中にある自然な声（Kyoko・O-Ren・Otoya、Samantha・Ava など。拡張・プレミアムが
   あればそれ）を選ぶ（`speechVoice.js`）。**iPad の「設定 → アクセシビリティ →
   読み上げコンテンツ → 声」で、日本語の拡張・プレミアムの声を入れておくとよい。**

あわせて:

- 英語の言い回しを直した（「1 prizes」と言わないよう、`{n:prize|prizes}` で単数・複数を
  出し分ける。「Coloured! 3 left」などの不自然な文）。0こ・0回のときは
  「0こ とれたよ」と言わず、「できた！ つぎは とれるよ」にした。
- 「ことばで伝える」は、英語表記でも日本語の文（「痛いです」）を英語の声に読ませていた。
  英語の文を足し（`content.js` の `PHRASE_EN`）、英語表記では画面も声も英語にした。
  記録（logEvent）は元の日本語のまま。英語表記でも文が日本語なら日本語の声で読む。
- 題名・案内の言い回しを、やわらかくした（「はじめます」→「はじめるよ」など）。

## 6. 残っていること

- 笑い声を録音に替える（5巡目で候補を出したが、利用者側で選び直し中）。カメ・タコ・カニも合成のまま
- iOS のプロジェクトを作るとき、ネイティブ側で `AVAudioSession` を `.playback` にする（§3.17）。
  消音でも効果音が鳴るか、スリープから戻って音が鳴るかを実機で確かめる
- 学ぶ画面の「どれかな？」の問いと答えは、英語表記でも日本語のまま（文字を えらぶ は日本語の遊び）
- PK戦（サッカー）版やダーツのような遊び（打ち合わせで例に出た。野球は入れた）
- App Store に出す前に確かめること: アプリ名と「NeuroNode」の表記（他社の製品名・商標。
  使ってよい範囲を確かめる）、プライバシーの説明（記録は端末の中だけ）、アイコンと
  起動画面、年齢区分の質問への答え（§3.10）
- 絵の差し替え（デザイン案の絵は仮のもの。「ぬりえ」「ふうせん」の絵も仮）
- **リールが1周の12分の1ほど空になっていた件**（2巡目の確認中に見つけた、main にもある
  欠陥）は、3巡目でこのブランチの**単独のコミット**として直した（`SLOT_ENGINE_VERSION` 1→2、
  detailed-design.md §0A.1）。main へ早く入れたいときは、そのコミットだけを cherry-pick できる
- 時間で進む遊び（リール・アーム・さかなつり）の画面そのものは、今回は絵柄・配色を
  変えていない。リールの枠を大きくする件は、刺激の見え方が変わるので
  `SLOT_ENGINE_VERSION` を上げるかどうかと一緒に決める。れんしゅうの回だけ大きく
  するなら、その回の条件として記録する（`session.config` → sanitize → CSV）必要がある
- 「中断からの再開」（デザイン案の画面）は入れていない。時間で進む遊びを途中から
  再開すると、1回の記録の中に空白ができる。回数だけの遊びなら可能

## 7. プレビューの公開（2026-09-27）

このブランチは本番サイトの下で見られる: https://kawano05.github.io/neuro/preview/
（本番 https://kawano05.github.io/neuro/ はそのまま）。

- GitHub Pages は1つのリポジトリに1サイト。公開（github-pages 環境）は main からしか
  許していないので、main の `.github/workflows/pages.yml` が本番をビルドしたあと、
  このブランチも `VITE_PREVIEW=1` でビルドして `dist/preview/` に同居させる。
  プレビューのビルドやテストが落ちても、本番の公開は止めない（プレビューが消えるだけ）。
- このブランチへ push すると `.github/workflows/preview-pages.yml` が main の
  pages.yml を起動し、サイトを作り直す（手で動かすなら `gh workflow run pages.yml --ref main`）。
- **プレビュー版は保存キーを分ける**（`neuronode-prototype-state-v4-preview`、
  `src/lib/content.js` の `isPreviewBuild`）。本番とプレビューは同じオリジン
  （kawano05.github.io）に載るので、同じキーだと1つの保存を取り合い、プレビューで
  試しに遊んだ回が本番の記録（CSV）に混ざる。プレビューでは設定も記録も最初から。
- 画面の左下に「プレビュー版（記録は本番と別）」と出る（押せない飾り、読み上げにも乗らない）。
- Service Worker は本番（/neuro/）とプレビュー（/neuro/preview/）で範囲とキャッシュ名が
  分かれている。本番の SW は通信優先なので、オンラインならプレビューの画面は
  プレビューのものが出る。
