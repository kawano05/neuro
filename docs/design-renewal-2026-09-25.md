# デザイン改修（はっきりした色）— 要望の整理と判断（2026-09-25）

ブランチ `design/hakkiri` で行っている、利用者の世界（スタート〜ホーム〜ゲーム〜
けっか）の見た目の作り直しの記録。**何を直したか**より、**なぜそう判断したか**と
**まだ何が残っているか**を残す（引き継ぎ書 `handoff-2026-08-17.md` と同じ流儀）。

入力は2つ:

- クライアントとの打ち合わせ動画（約53分）。前半15分で現行アプリを画面共有し、
  残りは口頭での議論。音声はローカルで文字起こしして読んだ（外部サービスには渡していない）。
- デザイン案 `nuro-design-hakkiri.html`（1180×820 のモックアップ7画面）。

> 動画・文字起こしには個人名や学校の情報が含まれるため、リポジトリには入れない。
> ここに書くのは、画面の要件として必要な内容だけ。

## 1. 打ち合わせで出た要望

括弧内は動画の時刻。

### 1.1 全体の方向

- **技術や機能はそのままでよく、問題はデザイン。**（13:13）
  機能自体は褒められている。いまの見た目は大人っぽく、
  支援者向けの画面に見える。（10:48, 11:23）
- 利用者は NeuroNode を使う重度の方で、何をやっても「初めての経験」になる。
  認知面は幼い子どもを想定してよく、**子ども向けと思われてもいい**。
  年齢に関係なく、みんなが楽しめる形にする。（9:56, 32:53, 34:14）
- 伝える相手は、機械が得意でないお母さん、作業療法士、学校の先生。
  「無理、難しい」と思われた時点で使われなくなる。（12:09）
- 目的は、市販のコミュニケーションアプリへ進むための**最初の練習**。（34:28）

### 1.2 画面の流れ

- スタート画面に小さく「せってい」があるので、**先に設定しないといけないと思った**。
  iPad のスイッチコントロールとアプリ側の設定の関係も、説明を聞くまで分からなかった。
  （4:59, 20:33）
- **ボタンはできるだけ少なく**する。表の画面は「はじめる」しかない、くらいでよい。（21:13）
- 画面の移動（ページめくり）は極力少なくする。何回も押す必要がある画面は、
  面倒で、それが「難しい」につながる。（38:59）
- 「走査停止」のような言葉は、普段目にしないので難しく感じる。（7:29）

### 1.3 メニュー（ホーム）

- 遊びは**絵のサムネイルで、1画面にすべて並べる**。次のページへ送らない。（11:48, 38:05）
- **いちばん簡単なものを左上、いちばん難しいものを右下**に置く。（38:25）
- どれから始めればよいのか、どれが難しいのかが分からなかった。
  **難しさを枠の中に書く**（かんたん／すこし むずかしい など）。（5:37, 6:52）
- 設定は支援者しか触らないので、**端に小さく**置く。走査で選べなくてよい。（23:55）

### 1.4 はじめの遊び（失敗のない遊び）

- 真っ暗な画面から、**押すと絵がポンと出てくる**だけでよい。イルカが出て消え、
  次は亀、次はバナナ……のように。言葉の説明はいらない。（9:12〜10:22）
- 力を入れたら画面が反応する、だけのものがまず要る。NeuroNode では「押した」
  感覚そのものが無いので、何をしたら何が起きたのかが最初は分からない。（21:49）
- **失敗がほぼ無く、やったことが全部プラスになる遊び**を増やしてほしい。
  利用者は自分でできた経験が少ない。（18:26）
  例: 風船が押すたびに割れる、塗り絵の絵がだんだん現れる。時間制限は無くてよい。
- 現行の「色と音」は、機能はそのままで絵を変えれば、最初の遊びとして使える。（11:04）

### 1.5 タイミングの遊び（リール・さかなつり・アーム）

- 仕様はいまのままでよい（速さを変えられる）。**絵を変える**くらいでよい。（20:06）
- リール: 枠を大きく、周りの余計なものは要らない。止まったときに
  「当たった」と分かる派手な演出がほしい。間違えたときはへこませず、
  あっさり次へ。いまの前向きな言葉（もう一回がんばろう）は良い。（14:30〜15:58）
- さかなつり: アタリのときに**大きなビックリマーク**が出れば、押す時だと分かる。
  いまは下に小さく「アタリ」と出るだけで気づきにくい。（17:24〜18:09）

### 1.6 けっか

- 「おわりました」は硬い。「できた」でよい。**最小限の情報**で、
  点数と「よくできました」「きみはプロだ」のような一言でよい。（16:44〜17:19）

### 1.7 音

- 音はとても大事。画面を見られない・顔を向けられない利用者にも届く。
  読み上げより、効果音（ボカーン、ボヨーン）のほうが反応がよい。（34:56〜35:49）
- ただし**強すぎる音ばかりだと発作を起こす人もいる**。楽器の心地よい音から
  びっくりする音まで、**遊びごとに選べる**ようにしてほしい。（36:18〜37:21）
- できたときに**笑い声や「やったー」**が入ると、周りが家族だけでも盛り上がる。（46:15）

### 1.8 設定

- 設定機能そのものは残してほしい。（23:31）
- 遊んでいる最中に「速いね」と思ったら、**その場で変えたい**。ホームへ戻るのが
  手間。**各ゲームの中に、支援者だけが触る設定ボタン**を置く。（26:21〜28:46）
- 設定の言葉が難しい。**小学校高学年が読んで分かる**くらいに。
  研究者向け（測定）の項目は分けたほうがよい。（28:52〜29:47）
- 最初の画面だけでよいので、支援者向けの簡単な説明書があるとよい。（24:41）

## 2. デザイン案の判定

**方向は合っている。そのまま実装できない点と、要望から漏れている点がある。**
直してから実装した。

### 2.1 要望に合っている点（採用）

| 要望 | 案での扱い |
|---|---|
| 表の画面は「はじめる」だけ | 絵＋「おして、はじめよう。」＋「はじめる」。せっていリンクを消した |
| 絵のサムネイルを1画面に、簡単→難しいの順 | 大きな1番（左上）から5番（右下）までのグリッド |
| 難しさを枠の中に | 「はじめては ここ」「なれたら」「チャレンジ」の札と①〜⑤の番号 |
| はっきりした色 | 遊びごとに色を分け、カラーユニバーサルデザインの推奨配色を使用 |
| 設定は端に小さく、走査の外 | 右上の「支援者の設定」。走査対象にしていない |
| 真っ暗な画面から絵が出る | 「おすと でてくる」（黒地に動物が出る。5回で終わり、失敗なし） |
| 最小限のけっか | 「できた！ たのしかったね」＋出てきた動物＋2つのボタン |
| ゲームの中の設定 | 遊びの上部に「この遊びの設定」。背景・押したときの音・声を選べる |
| 音を選べる | 楽器の音／明るい効果音／なし |

### 2.2 そのままでは採れない点（直した）

| 案の内容 | 問題 | 直し方 |
|---|---|---|
| Google Fonts（BIZ UDPゴシック・Zen丸ゴシック）を読み込む | **オフラインで動くことが要件**。iPad の WKWebView でネットワークが無いと文字が崩れる | 端末の丸ゴシック（iPad は ヒラギノ丸ゴ）を使う。字形は近い |
| 「高い音」「絵」「遊び」などに**ふりがなが無い** | 利用者向けの文字は総ルビ（`i18n.js`）が既存の決まり。テストもある | 文言は全部 i18n を通し、ルビを付けた |
| はじめる ボタンだけが押せる | スタートは「画面全体が入力」（詳細設計 §2.2）。狙って押せない利用者がいる | 見た目は案どおり、当たり判定は画面全体のまま |
| 1180×820 の横向き1種類だけ | iPad 縦・スマホでも使われている | 横向き・縦向き・スマホで並びを変える |
| 「はじめては ここ」 | 日本語として不自然 | 「はじめは ここから」 |
| アプリ名「NURO」 | 既存の名前と違う。既存の通信サービス名（光回線の「NURO」）と同じ綴りなので、使うなら商標の確認が要る | 名前は変えない（現行のまま）。決めるのは発注側 |
| 「色と音」のまえに「やりかた」の画面 | 最初のひと押しが「説明を閉じる」に使われ、何も出てこない。言葉の説明は要らないと言われた遊び | この遊びだけ「やりかた」を挟まない。画面の「押してみよう」が説明になる |

### 2.3 要望にあるのに案に無いもの

| 要望 | 今回の扱い |
|---|---|
| 点数のある遊び（リール・アーム・さかなつり・高い音だけ）のけっか | **追加した**。一言（前向きなものだけ）＋「○回のうち ○回 できたよ」＋星。細かい数値は支援者むけに畳んだ |
| 画面のことば「走査停止」「入力」のボタン | **利用者の画面から外した**（§3.5）。画面のボタンで押したい人向けに、設定で「おす」1つだけ出せる |
| リール・アームの速さを遊びの中で変える | **追加した**（§3.2）。「この遊びの設定」から。そくていの回は変えられないので、ボタン自体を出さない |
| さかなつりの大きな「！」 | **追加した**。れんしゅうの回の「アタリで つる」だけ（§3.3） |
| リールの当たり演出 | **追加した**。星がはじける。れんしゅうの回だけ（§3.3）、メダルにはしない（§3.4） |
| 「やったー」 | 「おすと でてくる」の設定で あり／なし（読み上げ） |
| 笑い声 | 未。録音素材が要る |
| 失敗の無い遊びを増やす（風船・塗り絵） | 未。次の候補 |
| 支援者向けの簡単な説明書 | 未（紙または別ページ） |
| 設定画面の言葉をやさしく／研究者向けを分ける | 未。次の候補（タブ構成は既に「そくてい」を分けてある）。遊びの中の設定は、やさしい言葉で書いた |

## 3. 判断の理由

### 3.1 「年齢中立」をやめた

詳細設計 §2.3 は、ホームを「年齢中立のアクティビティ」として作ると決めていた。
今回それをやめ、利用者の世界は**子ども向けに見えてよい**側へ振った。
クライアントが明言しており（1.1）、年齢中立の見た目が「大人っぽくて難しそう」に
見えていた、というのが打ち合わせで分かったこと。

支援者の世界（設定・評価ログ）は業務画面のまま。こちらは「分かりにくい」とは
言われたが、「子どもっぽくしてほしい」とは言われていない。

### 3.2 時間で進む遊びの設定は「はじめから」にする

「その場で速さを変えたい」（1.8）に対して、リール・アームのように**時間で進む
遊びは、設定を変えたら その回を中断して、はじめからやり直す**ようにした。

1回の記録（セッション）は1つの条件で行われたことが前提になっている
（`session.config` に速さを書き、解析で束ねる）。途中で速さが変わると、
その回がどちらの条件の記録なのか書けない。中断した回は `aborted` で残るので、
記録は失われない。

回数だけで進む「おすと でてくる」は、変えてもそのまま続ける（数えた回数は残る）。

### 3.3 そくていの回は見た目も変えない

さかなつりの大きな「！」やリールの当たり演出は、**れんしゅうの回だけ**に出す。
そくていの回（`difficultyMode: "measure"`）は、刺激の見え方を含めて固定のまま。

大きな「！」はアタリ音と同じ瞬間に出るので、目立ち方が変わると反応時間が
変わりうる。解析は「まず measure の回だけを見る」前提（引き継ぎ書 §2）なので、
れんしゅうの回に足すぶんには、測定の比較可能性を壊さない。

### 3.4 メダルは出さない

「当たったらメダルがパーンと出る」（1.5）は、リールの遊びでは**スロットの払い出し**
に見える。この遊びは賭博の表現を使わないと決めてある（詳細設計 §0A.5、README）。
当たりの演出は星と花丸にした。けっか画面の「メダル」も同じ理由で星にしている。

### 3.5 画面のスイッチ（ドック）を既定で出さない

利用者の画面の下にあった「走査停止」「入力」の2つは、打ち合わせで名指しされた
「分からない言葉」と「余計なボタン」だった（1.2）。

- NeuroNode・キーボードのスイッチは、ドックが無くても使える（押せば決まる）。
- 画面を直接さわる人は、タイルを直接押せる。
- 画面のどこを押しても「いまの枠を決める」使い方（狙って押せない人の画面スイッチ）は
  **設定で「画面に おすボタンを 出す」をONにしたときだけ**出す。

「走査停止」は利用者の輪から外した。走査を止めたいのは支援者で、
設定画面の「自動で うごかす」がその役をする。

### 3.6 iPad ではページに分けない

ホームのページ分割（`scanPaging.js`）は、画面の高さ 740px 以下を先読みで分けていた。
横長の画面（ノートPCのブラウザなど）では、グリッドにすれば6つとも1画面に入るのに、
先読みがページに分けてしまう（打ち合わせの画面共有で実際に「次のページ」が出ていた）。
グリッドで並べる画面では先読みをやめ、**描いてからはみ出したときだけ**分ける。
スマホの縦画面など、本当に入らない画面では従来どおり分かれる。

## 5. 確かめたこと

- `npm run test:unit` … 全部通る。足したテスト:
  - 並べ方: グリッドの幅では先読みで分けず、実測で入らなかったときだけ分ける
  - 保存: 足した設定4つが再読込で残り、知らない値は既定に戻る
  - けっか: 一言はいつも前向きで星は1つ以上、成功の数え方は遊びごとの連続記録と同じ
  - どれも、対象を壊すと落ちることを確かめてから入れた（リポジトリの流儀）
- `tests/web-smoke.mjs`（Playwright）
  - chromium-desktop は全部（29 ok・3 skip）
  - WebKit（ipad-portrait / phone-tall / phone-landscape / mobile-webkit-like）は、
    変えた画面に関わる検査だけを回して全部通した。**WebKit の4実寸の全検査は
    手元では回していない**（重いので CI に任せる）
  - 手元で一部だけ回せるように `SMOKE_PROJECTS` / `SMOKE_CHECKS` を足した
    （付けなければ今までどおり全部回る）
  - 変えた検査: 「色と音」の2本（おすと でてくる に合わせた）、ドックの前提
    （既定で出ない・設定で「おす」だけ出る）、iPad の読みやすさ（説明文は1番だけ
    画面に出す、行の高さの上限をやめて画面に届くかで見る）、Switch Control の往復
- 画面の実寸（Chromium）: iPad 横 1180x820 / iPad 縦 834x1194 / ノートPC 1366x650 /
  スマホ 390x812 はページをめくらずに6つとも入る。iPhone 14（390x664）は
  入りきらないので、これまでどおり3つずつのページに分かれる

見つけて直した欠陥（作っている途中に踏んだもの）:

- 設定を閉じたあと、フォーカスが設定ボタンに戻っていた。スイッチ機器の多くは
  Space / Enter を送るので、次のひと押しが遊びではなく設定ボタンを押し、また
  開いていた。閉じたら遊びの面へ返し、開いているあいだもダイアログの中へは
  フォーカスを移さない（利用者のひと押しで「明るい」などが押されないように）
- タイルの絵を枠いっぱいに切り抜くと、背の低いタイルでイルカが背びれしか見えなかった

## 6. 残っていること

- 設定画面（支援者の設定）の言葉をやさしくする。研究者向けの項目を見分けやすくする
- 失敗の無い遊びを増やす（風船が割れる、塗り絵が現れる）。デモ向けに「野球盤」のような1押しの遊び
- 笑い声・歓声の効果音（録音素材）
- 支援者向けの簡単な説明書（スタートとホームのボタンの説明）
- 絵の差し替え（デザイン案の絵は仮のもの）
- 時間で進む遊び（リール・アーム・さかなつり）の画面そのものは、今回は絵柄・配色を
  変えていない。リールの枠を大きくする件は、刺激の見え方が変わるので
  `SLOT_ENGINE_VERSION` を上げるかどうかと一緒に決める
- 「中断からの再開」（デザイン案の画面）は入れていない。時間で進む遊びを途中から
  再開すると、1回の記録の中に空白ができる。回数だけの遊びなら可能
