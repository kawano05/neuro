# neuro

`neuro` は、NeuroNode 利用開始時の導入訓練を支援する iPad 向けアプリの Web プロトタイプです。
単なる教材集ではなく、**タイミング入力課題（リズムゲーム）を中核に据えた導入訓練アプリ**として構成しています。

## 目的

本プロジェクトでは、NeuroNode 利用者が支援者と一緒に入力操作へ慣れるための訓練アプリを開発します。Web版で素早く試作・検証し、Capacitor によって iOS アプリ化することを前提にしています。

研究上の位置づけは、リズムゲームを「音楽ゲームのオマージュ」としてではなく、**感覚運動同期（sensorimotor synchronization; SMS）研究のタッピング課題をゲーミフィケーションした計測器**として設計する点にあります。聴覚キュー（時報型パターン: 低音のカウントイン→高音で押す）に対する入力時刻のオフセット（ズレ）を全試行で記録し、

- 利用者ごとの入力遅延の平均・分散の把握
- 走査間隔（scanInterval）等の設定値推奨の根拠データ
- 訓練前後の比較（導入訓練の効果測定）

に用います。キューは聴覚優先（画面注視が困難な利用者にも適用できるよう、視覚は補助表示に格下げ）とし、支援者向けの効果測定・評価記録機能はこの計測を下支えする継承機能として維持しています。

設計の詳細は `basic-design.md`（基本設計）・`detailed-design.md`（詳細設計）を参照してください。

## 画面フロー

利用者の世界（スタート〜ゲーム）と支援者の世界（タブ）を分離しています。

```
[スタート画面] → (1押しで AudioContext アンロック + 入力導通確認)
      │
      ▼
[アプリ選択]   → ゲームタイルのグリッド。走査で巡回、スイッチで決定
      │
      ▼
[ゲーム実行]   → 走査を完全停止し、画面全体が単一のスイッチになる
      │           （NeuroNode等の Switch Control との二重走査を構造的に防ぐ）
      ▼
[リザルト]     → 達成率・平均オフセット・ばらつき等を表示 → アプリ選択へ戻る
```

支援者向けビュー（効果測定・評価ログ・研究・操作訓練・設定）は既存タブとして残っています。操作訓練・効果測定・研究タブは「設定」画面の「研究者モード」トグル（既定OFF）で表示を切り替えます。設定・記録・研究データの変更は、各支援者ビューで「支援者編集を開始」を押したセッション中だけ有効です。このロックは認証ではなく、利用者の自前走査による誤操作を防ぐためのものです。

## あそび（ゲームタイル）一覧

アプリ選択画面には6枚のタイルが並びます。6種の別ゲームではなく、**同一の判定エンジンとログ基盤の上の難易度階段**です（パラメータだけが異なる同一エンジン、`src/lib/games/rhythm.js`）。

ホームには5枚の行が並び、リズム／さかなつり／まなぶ・つたえる は二階層目でさらに選びます。

| ホームの行 | 二階層目 | ゲームID | 訓練段階 | 内容 |
|---|---|---|---|---|
| いろと おと | — | `color-legacy` | L0 反応確認 | 押すと色と音が変わる（既存移植） |
| リズム | リズム れんしゅう | `rhythm-l1` | L1 合図入力（予告あり） | 時報型カウントイン→高音（押しどころ）で押す |
| リズム | リズム つづけて | `rhythm-l2` | L1-2 合図入力（連続） | カウントインは最初の1回のみ、以後は毎拍が押しどころ |
| リズム | たかいおとだけ | `gonogo` | L2→L3 橋渡し | 高音（Go）なら押す・低音（No-Go）なら見送る抑制課題 |
| アームを とめる | — | `crane` | 視覚必須 | 横→奥の順にアームを止め、床の上の位置を決める走査選択課題 |
| さかなつり | アタリで つる | `fishing` | 反応時間 | 合図が鳴ったら押す。前刺激間隔は乱数 |
| さかなつり | にせアタリに 気をつける | `fishing-gonogo` | 反応＋抑制 | 長靴（No-Go）を見送る |
| まなぶ・つたえる | マッチング / VOCA / 文字学習 | — | — | 教材（ゲーム契約には乗せない） |

`そくてい`（`calibration`）は利用者ホームには出さず、設定画面から支援者と一緒に実施します。基準オフセットの測定手順そのものなので、支援者の難易度設定を一切受け付けません。

いずれのゲームも入力時刻はゲーム側ではなくシェル（`src/lib/neuronodeApp.js` の入力ファネル）が `performance.now()` で確定し、契約経由でゲームへ渡します。全ゲームが同じ入口を通ることで、入力系遅延の測定条件が課題間で揃います。

## むずかしさ — 「そくてい」と「れんしゅう」

難易度は**セッションの目的**で2つに畳んでいます（`src/lib/difficultyMode.js`）。設定画面の「この回の つかいかた」で選び、どちらだったかは1回ごとに記録されCSVにも出ます。

| | そくてい（研究） | れんしゅう（訓練） |
|---|---|---|
| パラメータ | protocol 固定・**支援者は変更不可** | 支援者が自由に調整 |
| 画面の手がかり | 常にOFF | ONにできる |
| ねらいの通過音 | 常にOFF | ONにできる |
| クレーンのアシスト | なし | あり（連続失敗で許容が広がる） |

条件を1つずつ記録するだけでは足りません。条件が増えるほど層別すべきセルが増え、少ない参加者では空のセルばかりになります。「記録した」ことは「交絡が無い」ことを意味しない——だから束に名前を付け、解析ではまず `difficultyMode == "measure"` の回だけを見れば済むようにしています。

そくていの回は、むずかしさのつまみが無効化され、走査対象からも外れ、その理由が画面に出ます（効かない操作子を黙って置かない）。

### れんしゅうの段（訓練用の既定値）

実測して作り直しました。旧値は段になっていませんでした——L1 は10回押すのに68秒（0.148回/秒）、L2 は20回を24秒（0.833回/秒）で、**隣の段で入力密度が5.6倍に跳んで**いました。

テンポを50に揃えて、段のあいだで変わるのを**課題の構造だけ**にしています（テンポも変えると、難しくなったのが構造のせいかテンポのせいか分からない）。

| 課題 | 1回の長さ | 押す回数 | 入力密度 | 上がる軸 |
|---|---|---|---|---|
| リズム れんしゅう | 34秒 | 8 | 0.24回/秒 | — |
| たかいおとだけ | 28秒 | 12 | 0.43回/秒 | **認知**（押す/見送る） |
| リズム つづけて | 24秒 | 16 | 0.67回/秒 | **運動**（連続する拍） |

軸が1本でないことは意図です。`たかいおとだけ` の運動負荷が `つづけて` より低いのは、押さない試行があるので当然で、運動と認知を同時に上げないための設計でもあります。

そくていの protocol 値は `MEASUREMENT_PROTOCOL` に**別に持って**います。訓練の都合でプリセットを調整しても、測定の条件は動きません。

## 測定条件（記録されるもの）

支援者が変えられる設定のうち、**測っているものを変えてしまう**ものは条件として毎回記録し、CSVにも列として出します。禁止せず記録するのは、訓練としては必要な機能だからです（解析側で層を分けられるようにする）。

| 条件 | 既定 | ONにすると何が変わるか |
|---|---|---|
| `visualGuidance`（がめんに 手がかりを出す） | OFF | リズムの円が次の拍を予告し、押したあとにずれの目盛りが出る。入力が「聴覚キューへの同期」ではなくなる |
| `craneAudioGuidance`（ねらいの 通過音） | OFF | UFOキャッチャーで目標の座標が音になる。画面を見ずに解けるため、視覚必須課題でなくなる |
| `device`（端末） | 記録のみ | 画面の大きさ・視距離・刺激の実寸・スピーカー特性・音の出力遅延がまとめて変わる |

いずれも `session.config` / `session.device` に残り、`sanitize` を通過し、CSVの**末尾**に列として出ます（既存の列位置は動かしません）。3経路のどれか1つでも欠けると、条件の違う回をあとから区別できなくなります。

`そくてい`（`calibration`）は設定に関わらず常に手がかりOFFです。ここで得た中央値は判定窓の中心補正として全セッションに効くため、測る条件が支援者の設定で動いてはいけません。

## 走査（スイッチで選ぶ）まわりの約束

- **走査の現在位置は、いつでも画面に見えている。** 固定ドックと粘着タブバーのぶんを `scroll-margin` で避けます。
- **画面が短いときは一覧をページに分ける**（3項目＋「つぎの ページ」、最後のページから先頭へ循環）。走査で選ぶ相手はスクロールを止められないので、選ぶたびに画面が動くと「選ぶ」課題が「選ぶ＋動く画面を追う」課題に変わります。詰めるのは1ページあたりの項目数と飾りであって、タップ標的の大きさではありません。
- **タップ標的は44px以上**（Apple HIG / WCAG 2.5.5）。
- これらは目で見れば分かる一方、壊れてもビルドは通るので、`tests/web-smoke.mjs` が4つの実寸（デスクトップ・スマホ縦・iPad縦・スマホ横）で毎回確かめます。

## 起動

Node.js 22 以上を推奨します。

```powershell
npm install
npm run serve
```

ブラウザで `http://localhost:5173` を開きます。

## テスト

```powershell
npm run check
npm test
```

`npm test` は `test:unit`（判定ロジック・状態復元・CSV安全化・評価セッション整合性・走査のページ分割・効果音の音量上限・セッション推移・オフセット分布の単体テスト）と `test:web`（本番ビルド後にPlaywrightでスモークテスト）を順に実行します。

`test:web` は4つの実寸で走ります。

| プロジェクト | 実寸 | 何を見るためか |
|---|---|---|
| `chromium-desktop` | 1280x900 | AudioContext が要る検査（音の契約） |
| `mobile-webkit-like` | 390x664 | iOS Safari に近い狭い画面 |
| `ipad-portrait` | 834x1194 | 主対象の端末 |
| `phone-landscape` | 844x390 | **幅ではなく高さが足りない**狭さ。ここは長らく検査の外にあり、モバイル用の圧縮が丸ごと効いていなかった |

確認しているのは、スタート→アプリ選択→ゲームの通し、長押しとclick-only支援入力、キーボード操作、支援者ロック、自動走査停止、サブパスでのPWA配信とオフライン再読込、更新レース、そして次の「壊れてもビルドが通る」類です。

- 走査の現在位置が固定ドック/粘着タブバーの裏に回らないこと
- 全画面で横スクロール0・タップ標的44px以上・選択肢の名前が読める幅にあること
- リザルトに支援者用UIが出ないこと、文字入力中はドックが退避すること
- 効果音は設定で切れるが、**測定の合図音は切れない**こと（生成された AudioNode の種類を数えて見分ける）
- AudioContext が無い端末では、リズムとさかなつりがセッションを開かないこと（時計が止まったまま「刺激を出していない回のデータ」を作らないため）
- 実行中にページ例外・`console.error` が出ていないこと

### 実機が使えないときの見かた

`scripts/capture-screens.mjs` が3つの実寸で主要画面を撮り、CI が成果物として上げます（`artifacts/screens`）。ビルドとテストが緑でも「画面がどう見えるか」は分からない——余白の破綻も文字の折り返しも、テストを通り抜けます。判定はしないので、失敗しても CI は落としません。

```powershell
node scripts/capture-screens.mjs artifacts/screens
```

## iOS化

Mac + Xcode 環境で以下を実行します。

```bash
npm install
npm run build
npm run cap:add:ios
npm run cap:sync
npm run cap:open:ios
```

`cap:add:ios` は CocoaPods 版の Xcode workspace を生成します。CI とローカル検証では `ios/App/App.xcworkspace` を `App` scheme でビルドします。

Windows上ではXcodeや本物のiOS Simulatorは使えないため、GitHub Actions の macOS runner で Capacitor iOS プロジェクト生成とXcodeビルド確認を行います。最終的な Switch Control、Guided Access、NeuroNode実機操作は iPad 実機で確認します（`basic-design.md` §10・`docs/testing-without-apple-devices.md` 参照）。

## 操作

- `Space` または `Enter`: シェル画面ではハイライト中の項目を選択／ゲーム中は画面全体への入力として扱う
- `ArrowRight`: 走査ハイライトを手動で次へ移動（シェル画面のみ）
- `Escape`: シェル画面では走査停止／ゲーム中はゲームを中断してホーム（またはアプリ選択）へ戻る
- 画面下部の「入力」ボタン: 単一スイッチ入力の代替（シェル画面）
- ゲーム画面は全画面が単一のスイッチ（タップ・クリック・Space/Enter）

## 実装メモ

- フロントエンド: Svelte + Vite
- 音: Web Audio（オシレータ合成、先読みスケジューラ `createBeatScheduler`）。音源ファイルは使用しない
- iOS化: Capacitor
- データ保存: localStorage（`neuronode-prototype-state-v3`。リズム計測CSVが研究の主データ、既存の効果測定CSVは補助データ）
- 支援者向けの図: 評価ログの「かいごとの うつりかわり」（課題×条件で束ねた推移）と、研究タブの「入力オフセットの分布」（課題×テンポ×参加者ごと、手がかりの有無を2系列で比較）。どちらも母集団の違うものを1つにまとめない
- 公開: GitHub Pages
- オフライン: ビルド時にindex・ハッシュ付きWeb資産・manifest・iconを列挙し、Service Workerのinstall時に内容ハッシュ版の不変cacheへprecache。オンライン時はnetwork-firstで最新応答を返し、cacheは次版SWのinstall時に版単位で更新（Capacitorでは登録しない）
- CI: 単体・Web煙テストでPages公開をゲート + macOS上のCapacitor iOSビルド確認
